単発フローの実装段。**着手前に完了条件を宣言し、user の裁可を得てから実装に入る。**

台帳を持たないフローなので、着手前の合意は PR 本文に残る。その原型をここで作る。

1. 対象と完了条件を組み立て、**実装に入る前に** user へ提示する

   ```
   ## 対象
   {変更・新規作成するファイルをすべて列挙。新規は (新規) を付記}

   ## 完了条件
   - {何が真になれば終わりか。「実装した」ではなく、確かめられる状態で書く}

   ## 保証
   - 新たに宣言する保証: {この変更後に成り立つべき振る舞い}
   - 維持する保証: {壊してはいけない既存の振る舞い}
   ```

   - 完了条件は「どう確かめるか」が1行で書けるものにする。書けないなら粗すぎるので割る
   - 保証台帳 `docs/guarantees.md` があれば、変更が触れる範囲の保証はそこから引いて「維持する保証」に列挙する
   - テストを伴わない変更は `保証: なし（理由）` と明示する。無記載は不可
   - **user が保証を裁可するまで実装に入らない。** 削る・足す・直すの指示があれば反映してから進む

2. 作業ブランチを切る（`work/{slug}`）。既に作業ブランチ上なら `git status` がクリーンであることを確認する
3. 対象ファイルを読んで実装する
4. リポ CLAUDE.md の「静的チェック / 検証手段」に従い提出前確認を行う。コードを読んで caller・import の整合性も確認する。実行系・デプロイ系コマンド（rebuild / deploy / 本番起動）は実行しない
5. 保証台帳の記載に変更が出る場合（新保証・変更・廃止）、テストと同じコミットで台帳を更新する。更新漏れは実装未完了として扱う
6. `git add {変更したファイル}` し、`git diff --name-only --cached` が 1 で宣言した「対象」と完全に一致することを確認する。一致しなければ実装に戻る
7. コミットする。メッセージ本文に 1 の完了条件と保証をそのまま入れる（`hand-off` がこれを PR 本文の下敷きにする）
8. push・PR 作成はせずに止まり、user に確かめてほしいことを並べる。該当が無い項目も「なし」と書く。
   「差分を見てください」だけで止めない
   - **確かめてほしい動き**：画面に変更があれば、開く道順と見る点。画面に変更が無ければ、そう明言したうえで、
     user が走らせるコマンドと出るはずの結果（件数・値）
   - **宣言から外れたこと**：保証台帳に足した・変えた保証など、1 で宣言していないもの。根拠を添えて採るかを聞く
   - **実装で決めたこと**：仮に置いたこと、捨てた案

   裁可はここで受け切る。OK が出たら、次は `hand-off` である旨を伝える

対象が途中で1に宣言した範囲を超えたら、勝手に広げずそこで止まり、宣言を作り直す。

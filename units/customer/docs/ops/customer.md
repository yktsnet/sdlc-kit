# 顧客を理解して要件を決める（customer）

依頼主のいる案件で、顧客理解担当が利用者の現場と試作から何を作るべきかを引き出し、要件を決め、開発側へ返す。
`flow-client` に重ねて入れる。問いの Issue の欄と扱いは `flow-client` の [client.md](client.md) に従う。

## なぜこの形なのか

**AI で実装が速くなると、ずれたものを速く作ることが失敗になる。** 何を作るかの理解が足りないまま作ると、
作り直しで、速くなった分の時間が消える。

問いを立てて答えを待つだけでは、聞いたことにしか答えが返らない。利用者が言葉にしない困りごと、慣れで
回避している手間、資料に書かれていない例外は、現場を見るか、動くものを触ってもらわないと出てこない。

そこで、利用者よりも顧客を理解している人を1人置き、その人が要件を決める。要件の文書を書く仕事は
Claude に移し、その人の時間を顧客と向き合うことに使う。

## 担当

| 担当 | 受け持つこと |
|---|---|
| 顧客理解担当 | 要件を決める。現場を見て利用者に聞く。試作を利用者より先に触り、FB（フィードバック）を開発側へ返す。依頼主に照会して答えを回収する。要件の正本の直しをマージする |
| 実装担当 | 試作を作り、FB を受けて直す。依頼主への問いを立てる。ときどき顧客理解担当の現場と打ち合わせに同席する。`flow-team` の三役もこちらに属する |
| 利用者 | 試作を使い、気づいたことを返す |
| 依頼主の決裁者 | スコープ・やらないこと・費用と期日に了承を出す |

依頼主の了承が要るもの（スコープ、やらないこと、費用や期日に響くもの）は、顧客理解担当が案を作り、問いの Issue で
了承を取る。了承を待つあいだは、`flow-client` の「仮に置いて作る」に従って作り進めてよい。

**顧客理解担当は機能の細部を先に決めきらない。** 細部は実装担当が試作で決める。顧客理解担当が現場で見たことを
実装担当が知っていれば、細部を指示しなくても、何のための機能かを分かって作れる（「実装担当を巻き込む」）。

1人が顧客理解担当と実装担当を兼ねてもよい。兼ねるときも、試作を利用者の目で触る時間を別に取る。

**顧客理解担当には、依頼主の決裁者と利用者の両方に会いに行ける人を充てる。** 要件を決め、了承を取るのはこの担当なので、
依頼主との窓口を務められる立場が要る。業務の流れを自分の言葉で説明できる必要があり、コードを書けることは求めない。
GitHub で Issue と PR を読み書きできればよい。

## 顧客接点

顧客理解担当は、照会と打ち合わせのほかに、次の接点を自分で作る。

| 接点 | 何を得るか |
|---|---|
| 利用者の現場を見る | 質問では出てこない当たり前（作業の環境、手元の帳票、画面の外のメモ）。現物を見て「あれは何か」と聞ける |
| 利用者に話を聞く | 業務の流れ、実際の困りごと、試作が困りごとを解くか |
| 依頼主の決裁者と話す | 何のために作るか、何を優先するか、どこまでやるか |
| 依頼主との定例や、営業・保守の打ち合わせに同席する | 自分では聞けない立場の声。導入後に困っている所 |

**決裁者だけと話して終えない。** 依頼主との接点は決裁者が中心になりやすく、実際に使う人にとって使いやすいか、
現場の困りごとは何かが抜ける。利用者には別に会う。

### 仮説を持って聞く

聞く前に、業務の流れと困りごとの仮説を、実装担当と一緒に書き出す。質問はその仮説を確かめる形で作る。
仮説が無いと、聞き取りは手探りになり、答えを聞いても何が分かったかが残らない。聞いたあとは、仮説のどれが
当たり、どれが外れたかを記録に書く。

### 試作は実データに近づける

利用者に見せる試作は、利用者の実際の業務に近いデータで動かす。見慣れた値なら、利用者は自分の作業に当てはめて
答えられる。架空の値だと、意見が画面の見た目に寄る。データは Claude に作らせてよいが、依頼主の実データの
個人情報や金額をそのまま使わない。

## 社内レビューと利用者レビュー

試作は社内レビュー、利用者レビューの順で確かめる。**利用者レビューの前に、社内レビューを済ませる。**

| レビュー | 誰と誰 | 回し方 |
|---|---|---|
| 社内レビュー | 顧客理解担当と実装担当 | 顧客理解担当が試作を利用者の作業になぞって触り、使いにくい所・足りない所・現場と合わない所を実装担当へ返す。実装担当が直し、顧客理解担当が触り直す |
| 利用者レビュー | 顧客理解担当と利用者 | 打ち合わせで「元はこうだったのを、こう変えたがどうか」と見せて反応を聞く。直ったかを確かめる場にはしない。出た FB は社内レビューへ戻す |

社内レビューを先に済ませるのは、こちらで気づけたはずの指摘に利用者の時間を使わせないためである。利用者に聞くのは、
利用者にしか分からないこと（現場の例外、慣れた手順との違い、言葉の意味）に絞る。

変えた点を前と比べて見せると、利用者は自分の作業に当てはめて答えられる。社内レビューで顧客理解担当が出す FB も、
開発側へ渡すものは利用者の FB と同じ形の Issue にする（「FB を開発側へ渡す」）。

## 利用者から FB をもらう

利用者レビューの1回を、次の順で回す。

| 順 | 誰が | 何をする |
|---|---|---|
| 1 | 顧客理解担当 | 社内レビューを終えた範囲から、触ってもらう範囲を決め、利用者に頼む |
| 2 | 利用者 | 試作を触り、気づいたことを画面写真とコメントで送る |
| 3 | 顧客理解担当 | 届いた FB を仕分け、開発側へ渡すものを Issue にする（「FB を開発側へ渡す」） |
| 4 | 実装担当 | 渡された FB を見積もり、直し終わる日の見込みを顧客理解担当へ返す |
| 5 | 顧客理解担当 | 直ったものを社内レビューで触ってから、直し終わる日より後に打ち合わせを入れる |
| 6 | 顧客理解担当と利用者 | 打ち合わせで変えた点への反応を聞く。出た FB は 3 へ戻す |

頼むときは次を伝える。

- 触ってもらう範囲。その回で見てほしいのはこの範囲だと伝える。全部を渡すと、一度で全部を終えるものと受け取られる
- 気づいたことは画面写真に、気になる所とコメントを書き込んで送ること。1枚ごとに、どの画面で何をしようとしていたかを添えること
- 送り先は、利用者が普段使っている連絡の手段でよいこと
- 範囲の外のことも送ってよいこと

## FB を開発側へ渡す

届いた FB は1件ずつ、次のどれかに分ける。

| FB | 扱い |
|---|---|
| 要件どおりに動かない、要件にあるのに作られておらず予定にも無い | 開発側へ渡す |
| 画面の使い勝手（項目・並び・言葉・操作の手数） | 顧客理解担当が直し方を決め、開発側へ渡す |
| 要件の正本の記述が変わるもの（機能の有無・権限・データ項目・業務の手順） | 要件の変更とする。顧客理解担当が案を作り、依頼主の了承が要るなら問いの Issue で聞く。決まってから開発側へ渡す |
| 要件にあり、作る予定に載っている | 渡さない。作られたら確かめる |

開発側へ渡す FB は、`<FB のラベル>` を付けた Issue に1件ずつ書く。

```markdown
- 度合い：仕事が止まる
- 誰から：<利用者の立場、または顧客理解担当>

## 何が起きたか

<どの画面で、何をしようとして、何が起きたか。利用者の言葉のまま>

## 画面写真

<コメントを書き込んだ画面写真>
```

| 度合い | 当たるもの |
|---|---|
| 仕事が止まる | この画面では、その作業を終えられない |
| 手間が増える | 作業は終えられるが、今より時間か手数がかかる |
| 気になる | 作業に支障は無いが、言葉・並び・見た目が引っかかる |

**FB の Issue をそのまま実装の Issue にしない。** 相談者が `issue-draft` で実装の Issue を別に起こし、`根拠` に FB の
Issue を書く。FB の Issue には利用者の言葉が、実装の Issue には合意した直し方が残る。相談者は、度合いの重い FB から
起票する。実装の Issue がマージされたら、顧客理解担当が社内レビューで触って確かめ、FB の Issue を閉じる。

## 照会と回収

依頼主への問いは、`flow-client` の問いの Issue に置く。照会表・打ち合わせ・チャットは Issue から作る写しで、
依頼主は Issue を読まなくてよい。

| 何を | 誰が | skill |
|---|---|---|
| 送る問いを決め、答える人ごとの一覧を下書きする。送ったら `状態` と `照会の経路` を直す | 顧客理解担当 | `qa-send` |
| 照会表・議事録・チャットで出た答えを、当たる問いに写す。答えが揃った問いを閉じる | 顧客理解担当 | `qa-collect` |
| 写された答えを仮の案と突き合わせ、作業の Issue に反映する | 相談者 | `client-next` |

**答えを読んで次に何をするかを決めるのは、`client-next` だけにする。** `qa-collect` は写すところで止まる。
写す側と読む側で同じ答えの扱いを決めると、どちらで決めたかが分からなくなる。

## 要件の正本

決まった要件は `<要件の正本>` に置く。**要件の正本の直しをマージするのは顧客理解担当だけである。** 実装担当が
仮に置いた案は、作業の Issue の `仮定` に残し、要件の正本には書かない。仮の案と決まった要件が同じ文書に混ざると、
どれが依頼主の了承を得たものかが分からなくなる。

直しは Claude が書いて PR にし、顧客理解担当が読んでマージする。

### 要件の正本がまだ無いとき

最初の版は、依頼主の資料と、それまでの記録から Claude に起こさせる。依頼主から既存の要件定義書や仕様書を
受け取っていれば、それを `<要件の正本>` に移して始める。どちらでも、書けなかったところは空けたままにし、
聞くべきことを問いの Issue にする。

依頼主は、こちらが聞かないと言わないことがある。最初の版を起こす前に、次を聞いたかを確かめる。聞いていないのか、
聞いて「無い」と答えたのかは分けて記録する。

- 何の話か、誰の依頼か、扱う業務はいくつあるか
- いま誰が・いつ・何を使ってやっているか
- 何に困っているか（依頼主の言葉のまま）
- 通常の流れから外れる扱い（差し戻し・取り消し・やり直し）
- 既存のシステムとの連携と、切り替えのときに業務を止められるか
- 使う人と、立場ごとにできることの違い
- 今回やらないと話に出たもの
- 操作の手引き・研修・稼働後の運用を誰が持つか
- 件数と利用者数の桁、納期と予算
- AI に処理させる部分があるか。あるなら誤りに誰が気づくか、外へ送ってよいデータか

## 実装担当を巻き込む

**知って終わりにしない。** 顧客理解担当だけが分かっていても、作るものは変わらない。

- 現場や打ち合わせに、実装担当をときどき同席させる。テーマごとに同席する実装担当を決めておくと声をかけやすい
- 聞いたこと・見たことは、次の作業の前に実装担当へ共有する。記録を書いて終わりにせず、記録を指して、どの作業に関わるかを
  一言添える。相談者も、関係する記録を読んでから Issue を下書きする

## 記録を残す

**見たこと・聞いたことを、顧客理解担当の頭の中に溜めない。** 録画や議事録があっても、あとから引けなければ溜めていないのと
同じである。顧客理解担当が替わったとき、実装担当が理由を知りたいときに、テーマ・利用者・画面のどれからでも引ける形にする。

| 何を | どこへ |
|---|---|
| 現場で見たこと、聞いたこと、仮説の当たり外れ | `<顧客理解の記録>` に1回1ファイル。冒頭に、会った人の立場・テーマ・関わる画面を書く。原本（録画・議事録）は `<原本の置き場>` に置き、リポジトリに入れない |
| 開発側へ渡す FB | FB の Issue（「FB を開発側へ渡す」） |
| 依頼主の答え | 問いの Issue（「照会と回収」） |

原本をリポジトリに入れないのは、顧客の担当者名や金額などの実値が含まれるためである。

運用が始まって利用者が増えたら、聞き取りだけでなく使われ方の数字（操作の記録、問い合わせの件数）も見る。

## Claude に任せること

照会と回収、要件の正本の直しの分担は、それぞれの節にある。ほかの仕事は次のように分ける。

| 仕事 | Claude がすること | 担当がすること |
|---|---|---|
| 準備 | 既存の記録と要件の正本から、業務の流れの仮説と質問の案を出す | 実装担当と仮説を詰め、質問を決める |
| 記録 | 議事録・文字起こし・現場のメモを要約し、記録の形にする | 読んで直す |
| FB | 届いた FB と記録から、仕分けと度合いの案、FB の Issue と問いの Issue の下書きを作る | 仕分けを決め、OK を出す |
| 打ち合わせ | 議題（前回から変えた点、聞きたいこと）と案内の文面を下書きする | 日程を決めて送る |
| 試作のデータ | 利用者の業務に近いデータを作る | 実データに近いかを確かめる |
| 調べもの | 資料・現行システムのソースから、問いへの答えの案と根拠を出す | 採るかを決める |

## 取り込んだあとにやること

1. `flow-team` と `flow-client` が入っていることを確かめる
2. 穴を埋める

   | 穴 | 何を書くか |
   |---|---|
   | `<顧客理解の記録>` | 現場と打ち合わせの記録を置くディレクトリ |
   | `<原本の置き場>` | 録画・議事録・照会表の原本を置く、リポジトリの外の場所 |
   | `<要件の正本>` | 決まった要件を置く文書 |
   | `<FB のラベル>` | 開発側へ渡す FB の Issue に付けるラベル |
   | `<回答までの日数>` | 照会してから回答期限までの日数（`qa-send` が回答期限の既定に使う） |

3. 顧客理解担当を決める。実装担当と兼ねるかも決める
4. 2 で決めた FB のラベルを GitHub に作る
5. `CLAUDE.md` に、この文書への参照を1行書く。**規約そのものを書き写さない**

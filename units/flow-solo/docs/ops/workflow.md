# 作業フロー（1人）

着手前の合意を PR 本文に残す。Issue を立てない。決める人と作る人が同じなら、こちらを選ぶ。
作る人が複数いて、誰が何を持っているかを共有する必要があるなら `flow-team` を選ぶ。

## 入るもの

```text
.claude/skills/work/                      完了条件を宣言し、実装してコミットまで
.claude/skills/hand-off/                  完了条件を証拠で裏付け、PR を立てる。PR 本文の型を同梱
.claude/agents/completion-verifier.md     完了条件を work の宣言だけを基準に確かめる確認者
docs/ops/workflow.md                      この文書
```

## 一周の流れ

1. **宣言**（実装者）: `work` が対象・完了条件・保証を提示して止まる
2. **承認**（user）: 保証を読み、削る・足す・直す。**承認するまで実装に入らない**
3. **実装**（実装者）: 作業ブランチ `work/{slug}` を切って実装し、ローカルコミットで止まる
4. **レビュー**（user）: `work` が示した確かめてほしい動きを見て、`git diff main...{branch}` を読む。承認はここで受け切る
5. **引き渡し**（実装者）: `hand-off` が確認者（`completion-verifier`）に完了条件を判定させ、証拠を付けて PR を立てる
6. **マージ**（user）: PR を読んでマージする

マージは人が押す。`guards` のフックが `gh pr merge` を遮断する。ブランチと PR の単位は
[branch-and-pr.md](branch-and-pr.md) にある。

## 合意をどこに置くか

`flow-team` との違いは置き場だけである。1人のフローでは、着手前に宣言した完了条件と保証が
コミットメッセージ本文に残り、それがそのまま PR 本文になる。**残るものは変わらない。**

残作業の一覧は open な PR が受け持つ。これで足りなくなったら `flow-team` へ乗り換える。

## 証拠の無い完了を書かない

実装したという記憶も、コードがそこにあるという事実も証拠にならない。何を実行すれば真だと
言えるかを先に決め、実際に実行し、出力を PR 本文に貼る。

**実行して証拠を取るのは、実装者とは別のコンテキストで走る確認者である。** 作った本人は自分の意図
どおりに読むので、宣言から外れたところが見えない。テストも期待値も実装者が書くので、実装の出力を
期待値に写していれば、実装の誤りごと通る。確認者は実装者の説明を受け取らず、`work` の宣言だけを
基準に完了条件を実行し、証拠にしたテストの期待値も宣言から出し直す。直しはしない。

実装者側で完結しない確認（デプロイ後の動作・ブラウザ目視・実機確認）は、裏付けずに
`## 検証手順` へ回す。**ここで「確認済み」と書かない。**

## 乗り換える合図

`flow-team` へ移るのは次のいずれかが起きたとき。

- 作る人が2人目以上になり、誰が何を持っているかを PR の一覧だけでは共有できない
- open な PR が「着手待ち」を表すようになってきた（PR が実装より先に立つ）
- 「あれはどうなったか」に、PR の一覧から答えられない
- 着手前の合意を対話でしか残しておらず、後から確認する手段が無い

## 取り込んだあとにやること

1. `CLAUDE.md` に作業フローへの参照を1行書く。**規約そのものを書き写さない**
2. `CLAUDE.md` に静的チェックの表を書く（`work` の手順4がここを参照する）

   | 対象 | コマンド |
   |---|---|
   | `<言語 / 対象>` | `<コマンド>` |

3. 実行系・デプロイ系で実装者に踏ませたくないコマンドを `guards` の deny に足す
4. `.claude/agents/completion-verifier.md` は `model:` を書いていないので、呼び出し元のモデルを継ぐ。
   モデルを固定したいなら書き足す。配布元で固定すると、コピー先に古いモデル ID が残り続ける

この下の区切り線から先が日報の形。該当しない節は消す。

---

# 日報 YYYY-MM-DD

## 本日の実施内容

### 見出し

何が変わったか。それによって何が良くなるか。数字が出せるなら1つ添える。

[#00 Issue タイトル](../../../issues/00_slug.md) / [path](../../../path)

### 見出し

同上。Issue に紐づかない項目も同じ形で、成果物のリンクだけを置く。

[path](../../../path)

## 気づき

- 観察した事実 — 放置した場合に何が起きそうか。対処するかはここでは決めない

## 決定事項

- 何を採り、何を捨てたか

## 今後の対応

- タイトル — なぜ必要か一言

## マージ待ち

上から順にマージを依頼する。

- [#0 タイトル](PR の URL) — 何が入るか一言。CI グリーン
- [#0 タイトル](PR の URL) — 同上。**検証手順が未実施のため今回は見送り**

## 本報告の対象外

- 未 push: abc1234 —

---

**読み手は上司とステークホルダーである。** Issue も PR も開かずに、その日に何が進んだかが
この1枚で分かること。これが満たせないなら日報の意味がない。

## 見出しの階層

H1 は日付だけを持つ。節は H2、項目は H3。本文の構造は H2 と H3 が担うので、H1 に情報を
足さない。

## 本日の実施内容

成果の単位で H3 を立てる。見出しは読める語にする。作業フローの種類で書き方を変えない。

本文は**何が変わったか**と**それで何が良くなるか**の2点。実装の手段は書かない。
「CI を新設した」ではなく「提出前の自動チェックを入れた。壊れたものが main に入らなくなる」。
項目あたり2〜4行、5件を超える日は各2行までに抑える。

エンジニアでない読み手が意味を取れる語を選ぶ。ファイル名・コマンド名を主語にしない。
数字は完了条件や実測から取れるものを1つだけ。無理に付けない。

**各項目の末尾に、成果物へのリンクを1行で置く。** 本文を読んで中身を見たくなった人の入口
である。Issue があれば先頭に置き、続けてその項目の**中心になったファイル**を並べる。全件を
列挙しない。変更範囲は git log と PR が持つ。

PR へのリンクは置かない。読み手は PR を開かないので入口にならない。

ファイル名に空白が入る場合、リンクでは `%20` に置き換える。

## マージ待ち

open の PR を、マージする順に並べる。依存のあるものが先。無ければ番号順。

見送るものは理由を添えて明記する。承認者が上から順に押していける状態にしておくための節
なので、押してよいかの判断を承認者へ投げ返さない。

## 決定事項

その日に選択肢を捨てた判断を書く。何を採り、何を捨てたか。

**`JUDGE.md` があるなら、ここに書いたものが追記の候補になる。** 後から変えるとコストがかかる
判断だけを移し、決め手と見直す条件は user に聞き取る。理由を埋めない。

## 気づき

その日の作業中に実際に見えたものだけを書く。想像や一般論は書かない。対処が決まったものは
「今後の対応」に回す。判断が済んだものは「決定事項」へ移す。

## 書かない値

`<そのリポで地の文に書かない値（顧客名・金額・個人情報など）>` は書かない。例が要るなら
ダミー値を使う。

## 文体

常体で事実を述べる。「動いた」「積んだ」「取り上げた」のような口語は使わない。

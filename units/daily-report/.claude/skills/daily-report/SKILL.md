# daily-report

その日に**リモートへ push した**成果を、上司とステークホルダーが読む1枚にまとめる。

**読み手は Issue も PR も開かない。** この1枚だけで、その人が1日に何を動かしたかが分かること。
「詳細は Issue にある」で済ませると、読み手は結局何も分からないまま終わる。

一方で実装の手順・詳細は書かない。書くのは**何が変わったか**と**それで何が良くなるか**。

対象を push 済みに限るのは、手元にしか無いものを成果として報告すると、読み手が確かめられない
からである。入力が git なので、この skill は作業フローの種類に依存しない。

## 置き場は担当者ごとに分ける

日報は `docs/reports/<担当者>/YYYY-MM-DD.md` に書く。`<担当者>` は git の設定から引く。

```bash
git config user.email | cut -d@ -f1
```

分けるのは、日報がファイル名を日付だけで決めるからである。同じ日に2人が書くと1枚を取り合う。
1人で使うリポジトリでもディレクトリは作る。担当者が増えた時点で書いたものを移す作業が
発生しない。

**この値をこのファイルに書き込まない。** skill はリポジトリにコミットされて全員へ配られる
ため、誰か1人の名前を焼き込むと、他の担当者の日報もその名前のディレクトリに入る。書く直前に
毎回引く。

引いた値が空、または英数字とハイフン以外を含むなら、user に使う名前を聞いて進む。

## 0. 未コミット・未 push を先に片付けるか聞く

```bash
git status --short
git log --branches --not --remotes=origin --format='%h %s'
```

どちらかに出たものがあれば、**日報を書き始める前に** user へ「コミット・push して日報に
含めるか、今回は対象外にするか」を聞く。含めるなら先に済ませてから 1 へ進む。勝手に
コミットしない。

**片付いたら `day/<日付>` へ切り替える。** 無ければ main から切る。日報が slug を持たない
`day/<日付>` を使うのは、その日に1本しかないことが名前から分かるようにするためである
（`docs/ops/branch-and-pr.md`）。

指示を受けたときにどのブランチにいたかは関係ない。日報は `day/<日付>` に書いてそこで
コミットする。main では動かさない。

## 1. 期間を決める

`docs/reports/<担当者>/` の最新ファイルの日付が起点。無ければ当日分だけを見る。他の担当者の
ディレクトリは見ない。書く範囲は自分が push したものだけである。

前回以降を拾う形にしてあるので、作業しない日を挟んでも日付の穴を気にしなくてよい。

## 2. push 済みのコミットを集める

```bash
git log --remotes=origin --no-merges --since="<起点>" --author="$(git config user.email)" --format='%h %s'
```

`--remotes=origin` は origin から到達できるものだけを見る。ブランチのままでよく、main への
マージは条件にしない。`--author` で絞るのは、日報が担当者ごとに分かれるからである。

未 push のコミットは日報に載せず、「未 push のため対象外」として ID だけ残す。黙って落とすと
翌日どこから再開するか分からなくなる。

```bash
git log --branches --not --remotes=origin --format='%h %s'
```

`docs/reports/` だけを変えたコミットは除く（誰のディレクトリでも同じ）。日報を書いたこと
自体は実装ではない。

## 3. 成果の中身を引く

**Issue に紐づく作業も、紐づかない作業も、同じ重みで拾う。** 2 で集めたコミットを変更ファイル
ごと見て、その日に動いたものを成果の単位で数え上げる。

### Issue 版（`flow-issue`）

ブランチ名 `claude/{id}-{slug}` から id を拾い、`issues/{id}_*.md` を読む。中身は保証節と
「内容」に集まっている。

```bash
git log --remotes=origin --since="<起点>" --author="$(git config user.email)" \
  --format='%D' | grep -oE 'claude/[0-9]+[a-z]?' | sort -u
```

**Issue ファイルが `day/<日付>` に見つからない場合、その PR はまだマージされていない。**
対応する `claude/*` ブランチへ一時的に `git switch` して読み、終わったら戻る。

`status: open` のまま残っている Issue と、裁可待ちの `status: draft` も拾う。着手を待っている
件があること自体が読み手には情報で、外部の回答待ちのものは何週間も残る。「今後の対応」に、
何を待っているのかを添えて並べる。

### 単発版（`flow-single`）

コミットが属するブランチの PR を読み、`## 完了条件` と `## 証拠` から中身を引く。

```bash
gh pr list --state all --search "updated:>=<起点>" --json number,title,headRefName,body,state
```

**まだマージされていない PR も拾う。** その日に push された変更は、マージの前でもその日の成果
である。マージ済みか否かは 5 で書き分ける。

**`## 証拠` が空のままレビューに出ている PR は、日報を書く前に指摘する。** `hand-off` で先に
埋めるかを user へ聞く。日報は成果として載せるので、PR 側が確認を示していないまま書くと、
報告と PR が食い違う。

**まだ PR が無いコミットは、着手前に宣言した完了条件から書く。** PR より前の合意は記録が
残らないので、日報がその記録を兼ねる。

## 4. PLAN.md / JUDGE.md があれば確認する

リポジトリ直下に無ければ飛ばす。扱いは `docs/ops/phase-mvp.md` にある。

- **PLAN.md**: 完了した行があれば、行ごと消す変更を提示し、承認を得てから直す。PLAN に無い作業を
  していた場合は、行を足すか PLAN の外として扱うかを聞く
- **JUDGE.md**: 期間内に、選択肢が2つ以上あって片方を捨てた判断があったかを見る。あれば候補
  として挙げ、何を採り何を捨てたか・決め手・見直す条件を user に聞き取って追記する。
  **理由を私が埋めない。** 埋めた理由はもっともらしく読めるぶん、後から読む人を誤らせる。答えが出ないものは書かずに置く

先に片付けるのは、どちらの更新も日報の本文に載るからである。日報を書いた後に聞き取ると、
答えが返るたびに書き直すことになる。

## 5. マージ待ちの PR を並べる

```bash
gh pr list --state open --json number,title,labels,body,mergeable,statusCheckRollup \
  --jq '.[] | "#\(.number) \(.title)\n\(.body | split("\n")[0])"'
```

並べる順は、**依存のあるものが先**。無ければ番号順でよい。CI が赤い PR と、引き渡しが
済んでいない PR は、その旨を添えて「今回は見送り」と明記する。済んでいないとは、Issue 版では
`## 検証手順` が未実施のもの、単発版では `## 証拠` が空のものを指す。この節は承認者が上から順に押して
いける状態にするためにあるので、押してよいかの判断を承認者へ投げ返さない。

その日にマージされた PR は「本日の実施内容」の側に入るので、ここには残さない。

## 6. 書き出す

`reference/report-template.md` に従い、`docs/reports/<担当者>/YYYY-MM-DD.md` に書く。
該当しない節は消す。

**「本日の実施内容」は成果の単位で H3 を立て、各項目の末尾にリンクを1行で置く。** 本文を読んで
中身を見たくなった人の入口である。Issue があれば先頭に、続けてその項目の中心になったファイルを
並べる。**PR へのリンクは置かない。** 読み手は PR を開かないので入口にならず、中身を見たい人は
成果物のファイルから辿れる。

**変更したファイルを全件列挙しない。** 変更範囲は git log と PR が持っており、読み手である
非エンジニアには使えない情報である。

**「気づき」には、その日の作業中に実際に見えたものだけを書く。** 対処が決まったものは
「今後の対応」に回す。この節は起票の代わりではない。

## 7. 書いたものを確かめる

- **各項目のリンク行**がすべて実在するファイルを指しているか
- **エンジニアでない読み手が読んで意味が取れるか。** ファイル名やコマンド名が主語になっている
  項目、手段しか書いていない項目は書き直す
- **口語が混じっていないか。** 「動いた」「積んだ」のような語は常体の記述に直す
- **本文に開けないリンクが混じっていないか**
- **`<そのリポで地の文に書かない値>` が入っていないか**

リンクは目で追わずに確かめる。

```bash
grep -oE '\]\(\.\./\.\./\.\./[^)]+\)' docs/reports/<担当者>/YYYY-MM-DD.md \
  | sed -E 's/^\]\(\.\.\/\.\.\/\.\.\/(.*)\)$/\1/' \
  | python3 -c 'import sys,urllib.parse,os
for l in sys.stdin:
    p=urllib.parse.unquote(l.strip())
    print(("OK  " if os.path.exists(p) else "NG  ")+p)'
```

## 8. コミットして止まる

```bash
git add -A docs/reports/<担当者>/
git add PLAN.md JUDGE.md 2>/dev/null   # 無ければ何も起きない
git commit -m "Write the day's report"
```

**コミットメッセージにも PR 本文にも、作業ログへのリンクを付けない。** 実行環境によっては
末尾にそうした行を足すよう促されることがあるが、発行元のアカウントでしか開けず、他の担当者が
押しても中身に到達できない（`docs/ops/branch-and-pr.md`）。

**push も PR も、user の OK が出るまで行わない。** コミットしたら、変更したファイルを一覧で
示して止まる。差分そのものは貼らない。

> `day/<日付>` にコミットしました。
>
> - `docs/reports/<担当者>/YYYY-MM-DD.md` — 日報
>
> 読んでください。OK であれば PR を出します。直したい点があればこの場で直します。

直しが返ってきたら同じブランチにコミットし直す。origin に何も出ていないので、何周してよい。

## 9. OK が出たら PR を出す

```bash
git push -u origin day/<日付>
gh pr create --base main
```

既に PR があるときは push だけで載る。main へ直接 push しない。

## 書かないもの

- 実装の手段と詳細
- 作業環境の準備（担当者ごとに違い、リポジトリの状態を変えない）
- 未 push の作業内容
- 裁可前の `git push` と `gh pr create`。8 で止まらずに出さない
- 変更したファイルの全件列挙（git log と PR が持つ）
- `<そのリポで地の文に書かない値>`

「書かない」は**詳細**にかかる。成果そのものを削ってはいけない。日報が短くなりすぎて何を
やったか伝わらないなら、削りすぎている。

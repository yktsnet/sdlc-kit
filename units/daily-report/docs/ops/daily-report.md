# 日報

`daily-report` skill が、その日に**リモートへ push した**成果を1枚にまとめ、
`docs/reports/<担当者>/YYYY-MM-DD.md` に書く。`<担当者>` は書く人の git の設定
（`git config user.email` のローカル部）から、書く直前に引く。

## 何のためにあるか

読み手は上司とステークホルダーで、**Issue も PR も開かない。** この1枚だけで、その人が1日に
何を動かしたかが分かること。「詳細は Issue にある」で済ませると、読み手は結局何も分からない
まま終わる。

一方で実装の手順・詳細は書かない。書くのは**何が変わったか**と**それで何が良くなるか**。

日報は、この kit が配る他の置き場とは答える問いが違う。Issue や PR や `PLAN.md` は「リポジトリ
と変更がどうなっているか」に答え、後からこの仕事を辿る人が読む。日報が答えるのは「その人が
1日に何を動かしたか」で、主語が人であり、読み手も外にいる。だから日報だけが担当者ごとに
分かれる（`docs/design-philosophy.md`）。

入力が push 済みのコミットなので、**この skill は作業フローの種類に依存しない。** どちらの
フローとも組める。

## PR の本数

**PR はこまめに出してよい。** 複数の担当者が同じリポジトリを触ると、ブランチが長く生きるほど、
触る範囲が広いほど、他の変更とぶつかりやすくなる。小さく出して早く main へ入れれば、ぶつかっても
直す範囲が狭い。

**本数が増えることは問題にしない。** その日に何が進んだかは日報が1枚にまとめるので、読み手は
PR の一覧を追わずに進み具合を知れる。作業フローの単位を入れると `daily-report` も一緒に入るのは
このためである。

**中身の変わらない状態の切り替えは、近くの作業の PR に相乗りさせる。** `PLAN.md` の終わった行の
削除は、ぶつかりを減らすことにもレビューにもならないので、日報の PR に載せる。**相乗り先が
無ければ小さな PR を出してよい。** 相乗りのために変更を手元に溜めると、作業を進めるたびに移す
手間が生まれる。

## 取り込んだあとにやること

1. `docs/reports/` を作る（`.gitkeep` を置く）。担当者ごとのディレクトリは skill が作る
2. 各担当者が `git config user.email` を設定していることを確かめる。日報の置き場をここから
   引くため、未設定だと書けない
3. `.claude/skills/daily-report/SKILL.md` の 3 の節を、採った作業フローに当たる側だけ残して
   もう片方を削る（Issue 版／単発版）
4. `<そのリポで地の文に書かない値>` を埋める（顧客名・金額・個人情報など、日報に実値を
   書かないもの）
5. `reference/report-template.md` の節を、報告する相手に合わせて増減する
6. `PLAN.md` / `JUDGE.md` を持たないなら、SKILL.md の 4 の節はそのままでよい（無ければ飛ばす
   段になっている）

埋め残しはこれで探せる。

```bash
grep -rn "<[^>]*>" .claude/skills/daily-report
```

## 使い方

```
/daily-report
```

未コミット・未 push があれば、書き始める前に扱いを聞いてくる。日報自体は `day/<日付>` に
コミットし、**push と PR は user の OK が出てから**行う。日報は外に出る文書なので、本人以外の
目を通さずに公開へ進める理由が無い。

`day/<日付>` に slug を付けないのは、その日に1本しかないことを名前で示すためである
（`docs/ops/branch-and-pr.md`）。

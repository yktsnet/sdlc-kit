# 文書の書き方

このリポの Markdown（README・CLAUDE.md・PLAN.md・JUDGE.md・`docs/` 配下・PR 本文）と、
コード中の日本語コメントに当たる規範。

**規範の本体は3つある。** 文の書き方は `.claude/skills/jp-writing/SKILL.md`、文書の組み立ては
`.claude/skills/md-writing/SKILL.md`、Mermaid 図の描き方は `.claude/skills/mermaid-diagram/SKILL.md` にある。
ここには、規範を各リポに置く理由、リポ固有に決めること、書き手とは別のコンテキストで校正と点検を
受ける決まりを書く。

## なぜ書き手の手元ではなくリポに置くか

文体は、既存のファイルを真似て書けば揃うように見える。だが真似る先が無い場面がある。
リポジトリを起こした直後、全編を新規に書くとき、担当者が替わった最初の1本。成果物にしか
存在しない規則は、書き手が持ち込む既定に負ける。

だから `doc-style` は選ばせない。どの単位を入れるときも一緒に入れる。

## このリポで決めること

以下は jp-writing が決めていない。リポごとに書き足す。

| 項目 | このリポの決まり |
|---|---|
| 見出しの言語 | `<日本語 / 英語見出し+日本語本文>` |
| 文体 | `<ですます / である / 混合>` |
| コミットメッセージの言語 | `<日本語 / 英語>` |
| README の言語 | `<日本語のみ / 日英併記>` |

コミットメッセージと PR の言語は**このファイルが正本**にする。CLAUDE.md には書かない。
言語の規約を複数箇所に置くと、片方だけ直されて割れる。

## 書かないもの

- 日付入りの履歴コメント（「2026-01 時点で〜」等）。経緯は git log に任せる
- コードを読めば分かることの説明。コメントは WHY が非自明なときだけ書く

## 別のコンテキストで校正と点検を受ける

書いた本人は自分の意図どおりに読むので、自分の文の癖や、文書どうしの重複に気づけない。
規範をリポに置いても、当てる人が書き手だけでは見落としが残る。そこで、書き手とは別のコンテキストで
走る2つの役を置く。

| 役 | 見るもの | 直すか | 規範 |
|---|---|---|---|
| `jp-proofreader`（校正役） | 日本語の表現 | 直す | 本ファイルと `.claude/skills/jp-writing/` |
| `md-reviewer`（点検役） | 文書の組み立て（目的・記録・重複・リンク・入口） | 指摘だけ返す | `.claude/skills/md-writing/` |

どの作業フローでも、次の決まりで呼ぶ。skill はこの節を指す。

- 日本語の `.md` を書き換えたら、コミットの前に `jp-proofreader` を呼ぶ。渡すのは、ブランチの分岐元
  （`git merge-base HEAD origin/main`）から書き換えた日本語の `.md` のパスと、変わった行の範囲である。
  範囲は `git diff -U0` の hunk 見出しから取る
- 新しい `.md` を作ったか、見出しを足した・消した・別の文書へ動かしたときは、`md-reviewer` も並べて呼ぶ。
  渡すものは校正役と同じである
- 校正役の直しを読み、意図を変えた直しは戻してからコミットする。校正役が報告に回した点と点検役の指摘は、
  書き手が直すか残すかを決める
- 呼ぶのは1回で終える。戻した行や、報告を受けて直した行のために呼び直さない
- Issue と PR の本文は渡さない

## 取り込んだあとにやること

- `.claude/agents/` の定義は `model:` を書いていないので、呼び出し元のモデルを継ぐ。モデルを固定したいリポは、
  取り込んだあとに書き足す。配布元で固定すると、コピー先に古いモデル ID が残り続ける

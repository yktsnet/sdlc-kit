# mermaid-diagram

Markdown に図を置こうとしている書き手が、図にするかどうかと、どう描けば読めるかを決めるための
基準と手順。README・`docs/` 配下・PR 本文の図に当てる。ラベルの文は `jp-writing` に従う。

図の目的は、**その図が無いと伝わらないものだけを、読める大きさで描く**ことである。

## 前提

GitHub は ```` ```mermaid ```` フェンスを本文カラムの幅（約 768px）に縮めて描く。図は SVG に
変換せず、フェンスのままコミットする。変換すると、ダークテーマへの追従と差分での閲覧ができなくなる。

この前提から、**図の幅はそのまま文字の大きさになる**。横に広い図ほど字が小さくなる。

## 描くか、描かないか

**分岐・失敗経路・境界・対比のどれも無いなら、図にしない**。順番に起きるだけの処理は、
番号付きリストのほうが速く読める。

| 主題 | 図でしか表せない理由 |
|---|---|
| 分岐 | 条件で処理が割れて、また合流する。文章では分岐の先を読み終えるまで全体が見えない |
| 失敗経路 | リトライのループや、複数の終了状態。制御の流れは一列の文章に写せない |
| 境界 | デバイス・ネットワーク・信頼境界をまたぐ配置。subgraph でしか表せない |
| 対比 | before / after、あるべき姿と現状。並べること自体が主張になる |

「全体像」は主題にならない。描くと、分岐の無い一直線か、抽象度の混ざった図になる。全体像が
要るなら、ディレクトリ構成表かコンポーネント表で出す。

図をやめても、情報は捨てない。中身に合った形へ置き換える。

| 図の中身 | 置き換え先 |
|---|---|
| 順番に起きる処理の列挙 | 番号付きリスト |
| 名前と役割、名前とステージの対応 | 表 |
| 1ステップだけの変換 | 一文 |

描くと決めたら、**そのリポジトリでいちばん込み入った判断が1ノードに潰れていないか**を見る。
潰れているなら主題を取り違えている。そのノードを展開して描き、周りの流れは本文で書く。

## 幅

縦に伸ばしても字は小さくならず、横に伸ばすと小さくなる。

| 規則 | 理由 |
|---|---|
| `TD` を既定にする。`LR` はチェーンが4ノード以下のときだけ | `LR` の幅はチェーンの長さに、`TD` の幅は分岐の本数に比例する |
| エッジのラベルは最短にする。API の列挙・引数・条件式を載せない | ノードを増やさずに幅だけを増やす |
| ノードのラベルは全角12文字程度まで。詳細は図の下の本文に書く | 長いラベルは、その階層全体の幅を押し広げる |
| 横に並べる subgraph は2つまで。3つ以上なら `TD` で縦に積む | subgraph は枠と余白のぶん幅を取る |

しきい値は運用で動かしてよい。動かさないのは、幅が文字の大きさになるという前提のほうである。

幅は描画せずに見積もる。**いちばん広い階層のノード数 × その階層のラベル長 + エッジのラベル長の
合計**を目安にする。`LR` ならチェーン全体が、`TD` なら最も広い分岐の階層が、いちばん広い階層に
あたる。削る順は、エッジのラベル、ノードのラベル、向き、図の分割である。

## 形と線種

形と線種を使い分けると、幅を増やさずに情報を1つ足せる。全部が同じ四角と同じ矢印の図は、
その余地を使っていない。

| 記法 | 型 |
|---|---|
| `([ ])` | アクター（人、外部の呼び出し元） |
| `{{ }}` | サービス、変換器 |
| `[( )]` | データストア |
| `{ }` | 判断、分岐点 |
| `[/ /]` | 外部からの投入、ファイル |
| `[ ]` | それ以外の処理 |

| 記法 | 意味 |
|---|---|
| `-->` 実線 | ローカル、同一プロセス内 |
| `-.->` 点線 | ネットワーク越し、非同期 |
| `==>` 太線 | 人の操作、主経路 |

割り当ては固定しない。ただし、**1つの図の中では必ず揃える**。

ラベルの改行は `\n` ではなく `<br/>` で書く。ラベルに記号を含むときは `["..."]` で囲む。

## 抽象度を混ぜない

概念（ルート・フェーズ・レイヤー）と実体（プロセス・ファイル・サービス）を、同じ平面に
置かない。概念名の subgraph の外に具体的なミドルウェアが並ぶ形になったら、subgraph を
やめ、合流と分岐で構造を見せる。

## 分けるか、まとめるか

**1つの図に主題は1つである**。分けるかどうかは主題の数で決まる。
分けてよい軸は3つある。

| 軸 | 例 |
|---|---|
| 時間 | ビルド時 / 実行時、セットアップ / 定常運用 |
| 正常系 / 異常系 | 主経路 / 停止・リトライ・強制終了の経路 |
| before / after | 移行前 / 移行後 |

まとめる前に、片方の図が単独で主題を持つかを見る。持たない図は消す。

分けたら、各図に主題を示す見出しか一文を付ける。図をまたいで出るノードはラベルを揃え、
どの軸で分けたかを本文に書く（「以下は正常系。停止の経路は次の図」）。

## 書かないもの

ホスト名・IP・アカウント名をノードのラベルに書かない。図を画像にする必要が出ても、外部の
ホスティングに置かない。

## 新しく描く

1. **箇条書きで書く。** それで足りるなら図を作らず、「描くか、描かないか」の置き換え先に納める。
   大半はここで、図が要らないと分かる。この手順を飛ばさない
2. **主題を1つ決める。** 2つ以上あるなら、「分けるか、まとめるか」の3軸に当たるかを見て、
   図ごとに主題を示す一文を付ける
3. **対象を読む。** 分岐の条件・終了状態・配置先を推測で書かない。図は、すでにあるものを写す
4. **向き・形・線種を決める**（「幅」「形と線種」）
5. **幅を見積もる**（「幅」の数え方）
6. **図の下に本文を置く。** ラベルから削った詳細をここに書く。図と本文で同じことを二度書かない

## 監査する

ファイルに図が2枚以上あるなら、先にファイル全体で見る。

```
[ ] 各図が単独で主題を持っている（持たない図は消す。この確認を先にやる）
[ ] 分けた軸が「分けるか、まとめるか」の3つのどれかである
[ ] 各図に主題を示す見出しか一文がある
[ ] 1枚に主題が2つ以上詰まっていない
```

そのうえで1枚ずつ見る。

```
[ ] 主題がある（分岐の無い一直線なら、消して箇条書きに置き換える）
[ ] いちばん込み入った判断が1ノードに潰れていない
[ ] 「幅」の表の4つの規則に収まっている
[ ] 形と線種が図の中で揃い、ラベルの書き方が「形と線種」の末尾に合っている
[ ] 抽象度が混ざっていない
```

指摘して終わりにせず、**直した Mermaid をその場で書く**。主題ごと差し替えるなら、幅の調整では
なく描く対象を変えることになるので、いまの主題が成り立たない理由を1〜2文で添える。

## 確かめる

Mermaid の描画はローカルでは確かめられない。「前提」のとおり、SVG に変換して確かめることもしない。

- 構文は、ノード ID の重複、引用符の閉じ忘れ、subgraph の `end` 抜けを目で確かめる
- 幅は、「幅」の数え方で見積もる。実際の表示は user に委ねる
- 見た目を確かめる必要があるなら、GitHub のどのページで何を見るかを user に渡す

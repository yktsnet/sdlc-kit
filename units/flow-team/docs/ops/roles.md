# 三役

決定と実装を分ける。決定と実行を同じ時間の中でやると、決定が実行の都合に引きずられ、
後から検証できなくなる。

| 役 | 担当 | 動く場所 |
|---|---|---|
| **user** | 決裁者。フェーズと保証の承認、レビュー、マージ、デプロイ | — |
| **相談者** | 調査・設計・Issue 作成。**実装しない** | 開放チャット（main のチェックアウト） |
| **実行者** | Issue に基づく実装、確認を受けての直し、PR の作成。**main に push せず、マージしない** | 専用の作業ブランチ |

「user」は役名である。チームのうち、その Issue を承認し、実行者を起動する人が当てはまる。

## 境界

- 相談者は Issue を起票するところまで。起票したら止まる
- 相談者をエージェントが演じる場合も同じ。実装を頼まれたら Issue を `draft` ラベル付きで
  起票して止まり、user が保証節を承認して `draft` を外してから実行者を起動する
- 実行者は Issue に基づく実装から、確認者の判定と user の確認を経て PR を出すまで。進め方は
  [workflow.md](workflow.md) の「一周の流れ」にある。main への push・マージ・本番コマンドの実行は禁止
- 検証手順は実行者がコミットメッセージ本文の `## 検証手順` に書き、user が実行者のセッションで実施する

## 確認者

実行者のコミットを、Issue だけを基準に確かめる subagent（`.claude/agents/issue-verifier.md`）を置く。
三役のどれでもなく、実行者が呼ぶ道具である。

作った本人は自分の意図どおりに読むので、約束から外れたところが見えない。テストも期待値も実行者が
書くので、実装の出力を期待値に写していれば、実装の誤りごと通る。判定を作った文脈の外に置くために、
確認者は実行者の説明を受け取らず、Issue の `確認` と保証節を自分で実行し、`対象` と差分を突き合わせて合否と証拠を返す。
直しはしない。

挙動の正しさは確認者が確かめるので、user が実行者のセッションで見るのは、使い心地と、確認者が
判定できなかったもの（rebuild・deploy・実機が要る確認など）になる。

## 例外

Issue 駆動の硬直を緩めるため、次の3経路に限り相談者の直接編集を認める。

- **リアルタイム ops** — 事前に Issue 設計できない障害対応。そこから派生した実装は Issue 化する
- **単発例外** — user が「今回は例外で直接編集してほしい」と明示した回。対象ファイルと理由を
  一言添えて編集する
- **軽量経路** — 保証台帳に触れず、文書だけの変更（skill と agent の定義を含む。ファイルの数と行数は
  問わない）か、ロジックに触れない設定の変更（単一ファイル・数十行以内）。単発例外の宣言も不要

**常用化したら、作業フローを見直す。** 例外が常態なら、分業がいまの体制に合っていない。
作る人が1人に戻っているなら `flow-solo` へ移る。

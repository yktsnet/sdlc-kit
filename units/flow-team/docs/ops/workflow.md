# 作業フロー（チーム）

着手前の合意を GitHub Issue に残す。作る人が複数いて、誰が何を持っているか・何が承認済みかを
共有する必要があるなら、こちらを選ぶ。決める人と作る人が同じなら `flow-solo` を選ぶ。

役割の境界は [roles.md](roles.md)、ブランチと PR の単位は [branch-and-pr.md](branch-and-pr.md) にある。

## 入るもの

```text
.claude/skills/issue-draft/               相談者が Issue を設計して起票する。本文の型を同梱
.claude/skills/issue-work/                実行者が Issue に基づき実装し、確認を受けて PR を出す
.claude/skills/rework-review/             相談者がマージ済みの PR の手戻りを束ね、繰り返す原因を Issue にする
.claude/agents/issue-verifier.md          実行者のコミットを Issue だけを基準に確かめる確認者
docs/ops/roles.md                         三役と確認者の境界、分業を緩める3経路
docs/ops/workflow.md                      この文書
```

## 一周の流れ

```text
draft ──（user が保証節を承認）──> open ──（着手で assignee）──> PR ──（マージで Closes）──> closed
```

1. **起票**（相談者）: `issue-draft` で GitHub Issue を立て、`draft` ラベルを付ける
2. **承認**（user）: 保証節を読み、削る・足す・直したうえで `draft` ラベルを外す。
   **`draft` の無い open とは、承認済みという意味である。**
3. **着手**（user）: Issue に自分を assignee として付け、作業ブランチ `issue/{N}-{slug}` を
   worktree に切り、実行者をそこで起動する
4. **実装**（実行者）: `issue-work` に従って実装し、コミットする
5. **確認者の判定**（実行者）: 確認者（`issue-verifier`）が Issue だけを基準に確かめ、合否と
   証拠を返す。「否」は実行者が直して判定を受け直す。判定を受けたら止まる。確認者を置く理由は
   [roles.md](roles.md) の「確認者」にある
6. **確認と直し**（user と実行者）: user は判定の表と `git diff main...{branch}` を読み、使い心地と、
   確認者が判定できなかったものを確かめる。直す点は同じセッションで伝え、実行者が追加コミットで直し、
   判定を受け直す。OK が出るまで繰り返す
7. **公開**（実行者）: user の OK を受けて自分のブランチを push し、本文に `Closes #N` を
   入れた PR を出す
8. **マージ**（user）: PR を読んでマージする。Issue はマージで閉じる

**リモートに載るのは、user が実行者のセッションで確かめて OK を出したものだけになる。**
実行者が push できるのは自分のブランチだけで、main への push とマージは `guards` のフックが
遮断する。

**確認と直しを同じセッションで回す。** 実行者は実装の文脈を保ったまま止まっているので、
指摘をそこで直すのが最も安い。PR の前に別の Issue を起こすと、合意の置き場が2つに割れる。

**Issue はマージで閉じる。** 閉じるのを別の手で行うと、main に実装はあるのに Issue が open の
まま残る期間ができる。マージせずに PR を閉じれば、Issue は open のまま残る。

## 一覧の読み方

置き場が GitHub Issue なので、残作業の一覧は `gh issue list` でそのまま出せる。

| 状態 | 見分け方 |
|---|---|
| 承認待ち | `draft` ラベルが付いている |
| 着手できる | `draft` が無く、assignee も無い |
| 作業中・PR 待ち | assignee が付いている |
| 済み | closed |

**番号は GitHub が振る。** 起票する人が何人いても番号を取り合わない。マイグレーションや保証台帳の
区切りのように順に並べるものも、連番ではなく Issue 番号で名付けると、並行する Issue が同じ番号を
取らずに済む。

## 一次情報を洗ってから書く

要件は1か所にまとまっていない。仕様書・既存のコード・過去の Issue に散っている。起票する
相談者が作業の主な語でリポ全体を検索し、当たった資料を全文読んでから書く。抜粋で済ませると、
別の箇所にある要件が Issue から落ち、落ちた分は実行者には見えない。

「定めが無い」「存在しない」と書くのは、検索した語と範囲を添えるときだけにする。

## 読み手向けの文書は実装と同じ PR で直す

README や `docs/` のように、振る舞いを説明する文書は実装と同じ PR で直す。後回しにすると、
main の実装と説明が食い違う期間ができる。`issue-work` は差分が Issue の「対象」と一致することを
求めるので、直す文書は起票の段で「対象」に入れておく。

## 起動と片付けの手順

ここは各自の手元の道具で回す。下は素の `git` と `gh` で書いた最小形で、自分のシェル関数や
エイリアスに畳んでよい。

### 起動（3 に相当）

```bash
n=42; slug=fix-loader
gh issue edit "$n" --add-assignee @me
git fetch origin
git worktree add "../$(basename "$PWD").wt/${n}-${slug}" -b "issue/${n}-${slug}" origin/main
cd "../$(basename "$PWD").wt/${n}-${slug}"
# ここで実行者を起動し、issue-work に Issue 番号を渡す
```

worktree を使うのは、main のチェックアウトを汚さずに複数の Issue を並行で走らせるため。

### 片付け（7 と 8 の後）

worktree は PR を出したら消し、ブランチはマージの後に消す。

```bash
# PR を出したら: 実行者のセッションを閉じ、main のチェックアウトで worktree を消す
git worktree remove "../$(basename "$PWD").wt/${n}-${slug}"
```

ブランチは、マージの後に `branch-pr` の `branch-check.sh` がセッション開始時に消す。
PR の後に直しが要ったら、origin のブランチから worktree を作り直す。

マージせずに PR を閉じて捨てると決めたら、ブランチを `git branch -D` で消し、Issue の assignee を
外す。外すと、その Issue は「着手できる」に戻る。

## 派生 Issue

PR を出す前の問題は、6 の中で実行者が直す。新しい Issue にしない。

マージした後に問題が出たら、閉じた Issue を開き直さず、元の番号を本文で指す新しい Issue を
立てる。記録を上書きすると、何をどう承認したかが後から読めなくなる。

## 手戻りを記録し、仕組みへ返す

**一度やったことをやり直したら、PR 本文に残す。** 手戻りの多くは、手順・道具・ガード・Issue の
切り方のどこかが欠けて起きる。その場で直して済ませると、次の Issue も同じ欠けでやり直す。PR に
残せば、繰り返す原因を拾って直せる。

### 何を書くか

`issue-work` は PR 本文に `## 手戻り` の節を必ず置き、手戻りが無ければ `なし` と書く。節の無い PR と、
手戻りの無かった PR を見分けるためである。書くのは次のものである。

- 確認者の「否」と、それを直したやり直し
- 確認や CI が落ちて直したもの
- Issue の本文が足りずに止まったもの、user に聞き直したもの
- フックや deny が正しい操作まで止め、回り道したもの。止めて正しかったものは書かない
- Issue に書かれていない波及を手で直したもの

次のものは書かない。

- user の使い心地の直し。動くものを見てから決めるので、予定したやり直しである
- main を取り込むための作業
- その場で1分もかからずに直した打ち間違い

1つの原因を表の1行にする。同じ原因から続いたやり直しは1行にまとめ、回数を「失ったもの」に書く。

```markdown
## 手戻り

| 何が起きたか | 失ったもの | 原因の分類 | 仕組みで防げたか |
|---|---|---|---|
| 確認者が保証の1項目めを「否」とした。取り消した予約も重なりに数えていた | 確認者を1回再開した。約15分 | 実装者の不注意 | 防げない |
| CI の lint が、ローカルの確認に無い規則で落ちた | 直して push し直した。約5分 | 道具の欠け | 防げた：`CLAUDE.md` の静的チェックの表に、CI と同じ lint のコマンドがあれば |
```

**仕組みで防げたか**には、防げたなら、どのファイルのどこに何があれば防げたかを書く。防げたと書いた行は
「実装者の不注意」にしない。

### 原因の分類

| 分類 | 当たるもの | 直す先 |
|---|---|---|
| 手順の欠け | skill・`docs/ops/` に書いていない手順、書いてあるが誤っている手順 | skill・`docs/ops/` |
| 道具の欠け | 手で繰り返した確認や書き換えのうち、スクリプトにできたもの | スクリプト・CI |
| ガードの摩擦 | フック・deny が正しい操作まで止めた。止めた理由や通る書き方が分からなかった | フック・設定 |
| Issue の切り方 | Issue の本文が足りなかった、誤っていた、範囲が広すぎた | `issue-draft` とテンプレートの基準 |
| 実装者の不注意 | 手順も道具も揃っていたのに見落とした | 記録だけにする。2本以上の PR で繰り返したら、ほかの4つのどれが欠けているかを考えて読み替える |

### 束ねて Issue にする

相談者が main のチェックアウトで `rework-review` を呼ぶ。マージ済みの PR から節を集め、同じ原因が
2本以上の PR に出たものを候補として並べる。user が採った候補は、`issue-draft` で `draft` の Issue に
する。直しも Issue を経るので、承認と確認者の判定を通らない経路はできない。

## 取り込んだあとにやること

1. GitHub に `draft` ラベルを作る（`gh label create draft`）
2. `CLAUDE.md` に三役と作業フローへの参照を1行書く。**規約そのものを書き写さない**
3. `CLAUDE.md` に静的チェックの表を書く（実行者が提出前に回す手段）。Issue 本文の「確認」と
   `issue-work` の手順4がここを参照する
4. 起動と片付けの手順を、自分の手元の形に畳む
5. `.claude/agents/issue-verifier.md` は `model:` を書いていないので、呼び出し元のモデルを継ぐ。
   モデルを固定したいなら書き足す。配布元で固定すると、コピー先に古いモデル ID が残り続ける

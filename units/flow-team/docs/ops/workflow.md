# 作業フロー（チーム）

着手前の合意を GitHub Issue に残す。作る人が複数いて、誰が何を持っているか・何が承認済みかを
共有する必要があるなら、こちらを選ぶ。決める人と作る人が同じなら `flow-solo` を選ぶ。

役割の境界は [roles.md](roles.md)、ブランチと PR の単位は [branch-and-pr.md](branch-and-pr.md) にある。


## 一周の流れ

```text
draft ──（user が保証節を承認）──> open ──（着手で assignee）──> PR ──（マージで Closes）──> closed
```

1. **起票**（相談者）: `issue-draft` で GitHub Issue を立て、`draft` ラベルを付ける
2. **承認**（user）: 保証節を読み、削る・足す・直したうえで `draft` ラベルを外す。
   **`draft` の無い open とは、承認済みという意味である。**
3. **着手**（user）: どれに着手するかは、相談者に並べさせてよい（「次に着手するものを選ぶ」）。動いている Issue と
   ぶつからないかを確かめ（「並行して動かす」）、Issue に自分を
   assignee として付け、作業ブランチ `issue/{N}-{slug}` を worktree に切り、実行者をそこで起動する
4. **実装**（実行者）: `issue-work` に従って実装し、コミットする。画面に出る変更は、画面の操作役
   （`screen-operator`）にたどらせて Issue と突き合わせてから進める（[roles.md の「画面の操作役」](roles.md#画面の操作役)）
5. **確認者の判定**（実行者）: 確認者（`issue-verifier`）が Issue だけを基準に確かめ、合否と
   証拠を返す。「否」は実行者が直して判定を受け直す。判定を受けたら止まる。確認者を置く理由は
   [roles.md の「確認者」](roles.md#確認者)にある
6. **確認と直し**（user と実行者）: user は判定の表と `git diff main...{branch}` を読み、使い心地と、
   確認者が判定できなかったものを確かめる。直す点は同じセッションで伝え、実行者が追加コミットで直し、
   判定を受け直す。OK が出るまで繰り返す
7. **公開**（実行者）: user の OK を受けて自分のブランチを push し、本文に `Closes #N` を
   入れた PR を出す
8. **マージ**（user）: PR を読んでマージする。Issue はマージで閉じる

**リモートに載るのは、user が実行者のセッションで確かめて OK を出したものだけになる。**
実行者が push できるのは自分のブランチだけで、main への push とマージは `guards` のフックが
遮断する。

**確認と直しを同じセッションで回す。** 実行者は実装の文脈を保ったまま止まっているので、
指摘をそこで直すのが最も安い。PR の前に別の Issue を起こすと、合意の置き場が2つに割れる。

**Issue はマージで閉じる。** 閉じるのを別の手で行うと、main に実装はあるのに Issue が open の
まま残る期間ができる。マージせずに PR を閉じれば、Issue は open のまま残る。

## 一覧の読み方

置き場が GitHub Issue なので、残作業の一覧は `gh issue list` でそのまま出せる。

| 状態 | 見分け方 |
|---|---|
| 承認待ち | `draft` ラベルが付いている |
| 着手できる | `draft` が無く、assignee も無い |
| 作業中・PR 待ち | assignee が付いている |
| 済み | closed |

## 並行して動かす

**1つの Issue を、1つの実行者のセッションと1つの worktree で受け持つ。** 作る人が何人いても、
1人が複数のセッションを開いても、この単位は変わらない。実行者は自分の worktree で起動し、main の
チェックアウトでは起動しない。main のチェックアウトは相談者が使う。同じチェックアウトで2つの
セッションがブランチを切り替えると、互いの未コミットの変更が運ばれて混ざる。

**1人が同時に受け持つのは3本までにする。** 自分が assignee の Issue を数え、PR を出してマージを
待っているものも含める。user は止まった実行者のセッションごとに使い心地と残る確認を見るので、
受け持ちが増えるほど、確認を待つセッションが積み上がる。

**着手の前に、動いている Issue とぶつからないかを確かめる。** 相談者も起票のときに確かめるが、
起票から着手までのあいだに、ほかの人が別の Issue に着手していることがある。assignee の付いた
Issue の `対象` と差分を見て、次のどれかに当たるなら、先の Issue がマージされてから着手する。

- 同じファイルの同じ箇所を書き換える。箇所は関数や節の単位で見る。別の関数や節を直すだけなら
  当たらない。一覧の末尾へ書き足すだけのものも当たらない
- 共有の台帳や一覧の、同じ行を書き換える
- 片方の結果を見てからでないと、もう片方を作れない

起票のときに当たると分かったものは、後の Issue の `待ち` に先の番号を書く。`issue-work` は、`待ち` の
Issue が閉じていなければ止まる。

**並行する実行者のあいだに、取りまとめ役を置かない。** 調整は次の2つで片付く。

- PR を出す前に main を取り込む。先にマージされた PR との衝突は、あとから出す側が出す前に解く。
  解き方は `issue-work` の手順11にある
- PR を出したあとに衝突したら、origin のブランチから worktree を作り直し、実行者を起動して直す

**番号は GitHub が振る。** 起票する人が何人いても番号を取り合わない。マイグレーションや保証台帳の
区切りのように順に並べるものも、連番ではなく Issue 番号で名付けると、並行する Issue が同じ番号を
取らずに済む。

**多くの Issue が書き換える共有の1行は置かない。** 件数や最終更新日のような行を置くと、並行する
たびにその行で衝突する。

**画面やサーバーを立てるリポでは、worktree ごとにポートと環境を分ける。** 分けないと、1人の実行者が
画面を立てているあいだ、ほかの実行者は確認を待つことになる。

### 次に着手するものを選ぶ

user に「次に何をやるか」と聞かれたら、相談者は main のチェックアウトで次の順に並べ、報告して止まる。
誰が並べても同じ結果になるよう、本文とラベルだけから決め、候補を user に選ばせない。着手は user が行う。

1. `gh issue list --state open --json number,title,body,labels,assignees` で一覧を出す
2. 「一覧の読み方」の「着手できる」Issue を候補にする。`待ち` の Issue が閉じていないものは、理由を添えて外す
3. ほかの開いている Issue の `待ち` に挙がる数が多い順に並べ、同じ数なら番号の小さい順にする。待たれている
   Issue を先に作るほど、着手できる Issue が増える
4. user の受け持ちが3本になるまで、上から取る。assignee の付いた Issue と、先に取ったものとぶつかるものは、
   「並行して動かす」に挙げた3つの場合のどれに当たるかを添えて飛ばす
5. 取った Issue、飛ばしたものとその理由、残りの本数を報告する。取れる Issue が無ければ、起票を促す

## 一次情報を洗ってから書く

要件は1か所にまとまっていない。仕様書・既存のコード・過去の Issue に散っている。起票する
相談者が作業の主な語でリポ全体を検索し、当たった資料を全文読んでから書く。抜粋で済ませると、
別の箇所にある要件が Issue から落ち、落ちた分は実行者には見えない。

「定めが無い」「存在しない」と書くのは、検索した語と範囲を添えるときだけにする。

## 読み手向けの文書は実装と同じ PR で直す

README や `docs/` のように、振る舞いを説明する文書は実装と同じ PR で直す。後回しにすると、
main の実装と説明が食い違う期間ができる。`issue-work` は差分が Issue の「対象」と一致することを
求めるので、直す文書は起票の段で「対象」に入れておく。

## 起動と片付けの手順

ここは各自の手元の道具で回す。下は素の `git` と `gh` で書いた最小形で、自分のシェル関数や
エイリアスに畳んでよい。

### 起動（3 に相当）

```bash
n=42; slug=fix-loader
gh issue edit "$n" --add-assignee @me
git fetch origin
git worktree add "../$(basename "$PWD").wt/${n}-${slug}" -b "issue/${n}-${slug}" origin/main
cd "../$(basename "$PWD").wt/${n}-${slug}"
# ここで実行者を起動し、issue-work に Issue 番号を渡す
```

worktree を使う理由と、着手の前に確かめることは「並行して動かす」にある。

### 片付け（7 と 8 の後）

worktree は PR を出したら消し、ブランチはマージの後に消す。

```bash
# PR を出したら: 実行者のセッションを閉じ、main のチェックアウトで worktree を消す
git worktree remove "../$(basename "$PWD").wt/${n}-${slug}"
```

ブランチは、マージの後に `branch-pr` の `branch-check.sh` がセッション開始時に消す。
PR の後に直しが要ったら、origin のブランチから worktree を作り直す。

マージせずに PR を閉じて捨てると決めたら、ブランチを `git branch -D` で消し、Issue の assignee を
外す。外すと、その Issue は「着手できる」に戻る。

## 派生 Issue

PR を出す前の問題は、新しい Issue にせず「一周の流れ」の 6 で直す（「確認と直しを同じセッションで回す」）。
マージした後に問題が出たら、閉じた Issue を開き直さず、元の番号を本文で指す新しい Issue を
立てる。記録を上書きすると、何をどう承認したかが後から読めなくなる。

## 待ちと手戻りを記録し、仕組みへ返す

**Issue 1本のあいだに時間を失ったものを、PR 本文に残す。** 時間を失う形は2つある。一度やったことを
やり直す手戻りと、1回が長い工程の待ちである。どちらも多くは手順・道具・ガード・Issue の切り方の
どこかが欠けて起きる。その場で直して済ませると、次の Issue も同じ欠けで時間を失う。PR に残せば、
繰り返す原因を拾って直せる。

### 何を書くか

`issue-work` は PR 本文に `## 待ちと手戻り` の節を必ず置き、何も無ければ `なし` と書く。節の無い PR と、
何も無かった PR を見分けるためである。書くのは時間を失った次の2つだけである。

**手戻り**：一度やったことをやり直したもの

- 確認者の「否」と、それを直したやり直し
- 確認や CI が落ちて直したもの
- Issue の本文が足りずに止まったもの、user に聞き直したもの
- フックや deny が正しい操作まで止め、回り道したもの。止めて正しかったものは書かない
- Issue に書かれていない波及を手で直したもの

**待ち**：1回で10分を超えた工程（テスト・ビルド・確認者の判定など）。やり直していなくても書く

時間は概算で書かずに測る。コマンドは `time` を付けて流し、確認者は立てた時刻と結果が返った時刻の差を取る。
自己申告の概算は測った値とずれる。

次のものは書かない。

- user の使い心地の直し。動くものを見てから決めるので、予定したやり直しである
- main を取り込むための作業
- その場で1分もかからずに直した打ち間違い

1つの原因を表の1行にする。同じ原因から続いたやり直しは1行にまとめ、回数を「失ったもの」に書く。
待ちは工程ごとに1行にし、流した回数とそれぞれの時間を書く。

```markdown
## 待ちと手戻り

| 種類 | 何が起きたか | 失ったもの | 原因の分類 | 仕組みで防げたか |
|---|---|---|---|---|
| 手戻り | 確認者が保証の1項目めを「否」とした。取り消した予約も重なりに数えていた | 確認者を1回再開した。14分 | 実装者の不注意 | 防げない |
| 手戻り | CI の lint がローカルの確認に無い規則で落ちた | 直して push し直した。6分 | 道具の欠け | 防げた：`CLAUDE.md` の静的チェックの表に、CI と同じ lint のコマンドがあれば |
| 待ち | テスト用のデータを入れ直すために、全件の投入を流した | 3回。11分・12分・12分 | 道具の欠け | 防げた：入れた状態を保存して戻すスクリプトがあれば |
```

**仕組みで防げたか**には、防げたなら、どのファイルのどこに何があれば防げたかを書く。防げたと書いた行は
「実装者の不注意」にしない。

### 原因の分類

| 分類 | 当たるもの | 直す先 |
|---|---|---|
| 手順の欠け | skill・`docs/ops/` に書いていない手順、書いてあるが誤っている手順 | skill・`docs/ops/` |
| 道具の欠け | 手で繰り返した確認や書き換えのうち、スクリプトにできたもの | スクリプト・CI |
| ガードの摩擦 | フック・deny が正しい操作まで止めた。止めた理由や通る書き方が分からなかった | フック・設定 |
| Issue の切り方 | Issue の本文が足りなかった、誤っていた、範囲が広すぎた | `issue-draft` とテンプレートの基準 |
| 実装者の不注意 | 手順も道具も揃っていたのに見落とした | 記録だけにする。2本以上の PR で繰り返したら、ほかの4つのどれが欠けているかを考えて読み替える |

### 束ねて Issue にする

相談者が main のチェックアウトで `rework-review` を呼ぶ。まだ読んでいない PR（`rework-read` のラベルが無いもの）
から節を集め、同じ原因が2本以上の PR に出たものを候補として並べ、読んだ PR にラベルを付ける。user が採った候補は、
`issue-draft` で `draft` の Issue にする。直しも Issue を経るので、承認と確認者の判定を通らない経路はできない。

記録しても読まなければ、同じ原因で時間を失い続ける。読んでいない記録がたまったら、`issue-draft` が `rework-review` を
回すよう報告に添える（閾値は `issue-draft` の手順7）。

## 取り込んだあとにやること

1. GitHub に `draft` と `rework-read` のラベルを作る（`gh label create draft`、`gh label create rework-read`）
2. `CLAUDE.md` に三役と作業フローへの参照を1行書く。**規約そのものを書き写さない**
3. `CLAUDE.md` に静的チェックの表を書く（実行者が提出前に回す手段）。Issue 本文の「確認」と
   `issue-work` の手順4がここを参照する
4. 起動と片付けの手順を、自分の手元の形に畳む
5. 画面やサーバーを立てるリポなら、worktree ごとのポートと環境の分け方を決め、起動の手順に足す
6. 画面を持つリポなら、Playwright を入れ、開発サーバーの立て方と、仮のログインがあればその入り方を `CLAUDE.md` の検証手段に書く。
   操作役と確認者はどちらも、Playwright が無ければ画面を見ずに止まる。画面を持たないリポでは、`.claude/agents/screen-operator.md` を消してよい
7. `.claude/agents/issue-verifier.md` と `.claude/agents/screen-operator.md` は `model:` を書いていないので、呼び出し元のモデルを継ぐ。
   モデルを固定したいなら書き足す。配布元で固定すると、コピー先に古いモデル ID が残り続ける

以下の手順で Issue を実行する。`$ARGUMENTS` に Issue 番号を渡す。

**前提**: 実行者は実装してコミットし、確認者（`issue-verifier`）の判定を受け、止まって user の確認を受け、指摘をこのセッションで直す。user が OK を出したら、PR を出すまでが担当。マージは user が GitHub で押す。リモートへは自分のブランチを push するだけで、**main には push しない**。確認者を置く理由は `docs/ops/roles.md` の「確認者」にある。

**一度やったことをやり直したら、その場で worktree の外のメモに1行書き留める。** 確認者の「否」、確認の失敗、聞き直し、フックに止められた回り道などが当たる。書き留めたものは手順11で PR 本文の `## 手戻り` に写す。終わってから思い出すと、回数と時間が抜ける。何を書くかと原因の分類は `docs/ops/workflow.md`「手戻りを記録し、仕組みへ返す」にある。

1. `gh issue view {N}` で Issue を読む。`draft` ラベルが付いている、または `待ち` の Issue が閉じていないなら、報告して止まる
2. `git status` で、ブランチが `issue/{N}-{slug}` かつワーキングツリーがクリーンなことを確認する（ブランチと worktree は起動時に作成済み）。違えば報告して止まる
3. 対象ファイルを読んで実装する
   - 実装の前に、Issue の主な語でリポを検索し直す。`根拠` に無い資料で要件に当たるものがあれば、手を付ける前に user に確かめる
   - Issue の「対象」と「内容」から外れる作業に気づいたら、手を付ける前に「新しい Issue にする / この Issue の中で直す / 見送る」を user に聞く。黙って直さず、黙って捨てない
4. Issue の「確認」項目と、リポ CLAUDE.md の「静的チェック / 検証手段」に従い提出前確認を行う。コードを読んで caller・import の整合性も確認する。実行系・デプロイ系コマンド（rebuild / deploy / 本番起動）は実行しない
5. Issue の保証節が保証台帳 `docs/guarantees.md` の記載に影響する場合（新保証・変更・廃止）、テストと同じ PR 内で台帳（保証の文言と対応テストの表）を更新する。台帳の更新漏れは実装未完了として扱う
6. 日本語の `.md` を書き換えたなら、`jp-proofreader` に校正させる。新しい `.md` を作ったか見出しを足した・消した・動かしたなら、`md-reviewer` も並べて呼ぶ。渡すものと、直しと指摘の扱いは `docs/ops/doc-style.md` の「別のコンテキストで校正と点検を受ける」に従う。そのあと `git add {変更したファイル}` し、`git diff --name-only --cached` が Issue の「対象」フィールドと完全に一致することを確認する（保証台帳を更新した場合はそれも対象に含まれていること）。一致しなければ実装に戻る
7. コミットする（保証台帳を更新した場合は同じコミットに含める）。メッセージ本文に報告を入れる（手順11で PR 本文の下敷きにする）。一時ファイルは作らず、heredoc で標準入力から渡して1コマンドに収めること:
   ```
   git commit -F - <<'EOF'
   {type}: {タイトル}

   ## 変更内容
   {Issue の内容フィールドを展開}

   ## 保証
   {Issue の保証節の各項目 → それを固定したテスト（ファイル・テスト名）の対応。テストを伴わない場合は Issue と同じく `なし（理由）`}

   ## 静的確認結果
   {確認項目に対する結果。git diff --name-only --cached の出力を含める}

   ## 検証手順
   {実行者側で完結しない確認（実行・デプロイ・目視）を、リポ CLAUDE.md の検証手順の雛形に従って記載。なければ省略}
   EOF
   ```
8. 確認者（`issue-verifier`）に確かめさせる。渡すのは Issue 番号と worktree のパスだけで、何をどう作ったか・どこを見ればよいかは書かない
   - 「否」があれば手順3に戻って直し、手順4〜7をやり直して追加コミットする。そのうえで同じ確認者を再開させ、前回の判定のあとに足したコミットの範囲（`<前回の判定の HEAD>..HEAD`）だけを渡す。何を直したかは書かない。「否」が無くなるまで繰り返す
   - 「判定できない」は直さず、手順9の出力に残す
   - セッションが変わって再開できないとき、または直しが Issue の対象の半分以上に触れたときは、新しい確認者で最初から確かめる
9. push・PR 作成はせずに止まり、user の確認を待つ。user が見るものは `docs/ops/roles.md` の「確認者」にある。以下を出力する:
   ```
   ✅ Committed on {branch}: {type}: {タイトル}
   Review: git diff main...{branch}
   Verifier: {手順8の判定の表をそのまま}
   Check: {user に残る確認。確認者が判定できなかった項目と、その確かめ方。確認者が挙げた目的に届かない点と、Issue に足すかの問い。画面に変更があれば、使い心地を見てほしい画面と道順。いずれも無ければ「なし」}
   Next: 直す点があればこのセッションで伝えてください。問題なければ PR を出すよう伝えてください
   ```
10. 直しを頼まれたら、Issue の範囲内なら追加コミットで直す（手順3のスコープ外の扱いは同じ）。直した範囲について手順4の確認をやり直し、手順8と同じく確認者を再開させて判定を受け直してから、手順9の出力に戻る。直しで新しい Issue は起こさない
11. user が PR を出すよう明示したら、次の順で進める。明示が無いまま進めない
    1. `git fetch origin && git merge origin/main` で main を取り込む。並行する Issue が先にマージされていると、取り込まずに出した PR は衝突したまま止まる。一覧の末尾への書き足しどうしの衝突は、main の分・自分の分の順で両方を残して解く。既存の行を両側が書き換えた衝突は user に示して解く。取り込みで中身が変わったら、手順4の確認をやり直す
    2. `git push -u origin {branch}`
    3. PR を出す（base は main、題は手順7の実装のコミットの題）。本文はそのコミットの本文を下敷きにし、手順10の直しを反映した最終の状態に書き直す。先頭に `Closes #{N}` を置き、末尾に書き留めた手戻りを `## 手戻り` の表にして置く。無ければ `なし` と書く
    4. 以下を出力して終える。**マージはしない**
       ```
       ✅ PR: {PR の URL}
       Next: このセッションを閉じて worktree を消す → マージ（Issue はマージで閉じ、ブランチはマージ後に branch-check が消す）
       ```

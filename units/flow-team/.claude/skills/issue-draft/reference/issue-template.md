## Issue 作成ルール

### フィールド

- `対象` : 変更・新規作成するファイルをすべて列挙する。新規は (新規) を付記。振る舞いを説明する文書（README・`docs/`）を直すなら、それも入れる
- `目的` : 誰の何をどう変えたいか。確認者は `確認` と保証をすべて満たしても目的に届かない点を挙げる。`確認` の項目だけでは満たしても目的を外れた成果物を合格にしうるためである。
- `内容` : 概要のみ。実装仕様は下のセクションに書く
- `対象外` : 目的に近いが今回はやらないことを挙げる。実行者は気づいた改善があってもここへ手を広げない。無ければ `なし` と明示する（省略すると、考えていないのか書き忘れたのか区別できない）
- `仮定` : 要件の曖昧さのうち、user に質問せず相談者が判断で埋めたものを挙げる。質問しなかった判断はここ以外に残らない。無ければ `なし` と明示する
- `確認` : 実行者が提出前に行う静的確認。このリポの CLAUDE.md の検証手段を参照して埋める。例: lib 変更時は影響 caller をすべて列挙・修正済みであること。存在しないなら省略せず `目視確認` と明示する
- `根拠` : 一次情報を洗った跡。「定めが無い」と書くなら、ここに検索した語と範囲が要る
- `待ち` : 先にマージされるべき Issue の番号。当たるかは `docs/ops/workflow.md`「並行して動かす」の3つの組で決める

### ライフサイクル

状態の見分け方は `docs/ops/workflow.md`「一覧の読み方」に、マージ後に出た問題の扱いは同じ文書の「派生 Issue」にある。

### 保証節

- 保証は自然言語で書く。テストコードやテストファイル名の指定は補足であり、主体は振る舞いの宣言
- user は承認のときに保証節・`対象外`・`仮定` を必ず読み、削る・足す・直す
- テストを伴わない変更（ドキュメントのみ・cleanup 等）は `保証: なし（理由）` と明示する。無記載は不可
- リポに保証台帳 `docs/guarantees.md` がある場合、「維持する保証」は台帳から引く。台帳の記載に変更が出る場合（新保証・変更・廃止）は台帳を対象ファイルに含める
- 「廃止する保証」に挙げたものは、台帳があれば台帳からも外し、対応するテストの扱い（削除・書き換え）を詳細セクションに書く

### 粒度

分ける目的は2つある。約束を1つずつ承認して確かめることと、並行して進めることである。分けるほど確認と PR の手間が本数分かかるので、どちらの得にもならない分け方はしない。対象ファイルの数では決めない。ファイルの数は確かめる量とも約束の数とも比例しない。

次の4つを上から順に当てる。

1. **上限を超えたら分ける。** 次のいずれかに当たったら分ける
   - 要件から起こした確かめる項目（`確認` の項目と、新たに宣言する保証の行）が15件を超える。実装の往復と確認の手間が項目の数に比例して延びる。基準を数にするのは、超えたかどうかの解釈が起票のたびに揺れないようにするためである。静的チェック・既存テストの維持・文書の更新の行は数えない。ほとんどの Issue に付く行なので、数えると小さい Issue 同士もまとめられなくなる
   - 変える画面が2つ以上ある。ページ内の切り替えは数えない。使い心地の確認と直しの往復が画面ごとに増える
   - 確認手段が2種類以上ある（例: サーバ上での実行確認と、ブラウザでの目視確認）。画面に出る要件の API のテストと画面での確認は、1種類と数える
2. **並行して動かせないものはまとめる。** 作業中の Issue か、同時に書く Issue と、`docs/ops/workflow.md`「並行して動かす」の3つの組のどれかに当たり、まとめても 1 に当たらないなら1本にする。分けても1本ずつ順にしか進まず、後の Issue が前の Issue の変えたところを直し直すことになる。バックエンドとフロントエンドも「片方の結果を見てからでないと、もう片方を作れない」かで決める。画面に出る要件は API と画面で分けない

   まとめると 1 に当たるなら分け、後の Issue の `待ち` に先の番号を書く
3. **小さいものはまとめる。** 要件から起こした確かめる項目が3件以下の Issue は、同じ対象か同じ画面を変える Issue とまとめても 1 に当たらないなら、1本にする。小さい Issue では本数分かかる手間が実装より重くなる。まとめる相手が無ければ、そのまま1本にする
4. **それ以外は、保証台帳の区切り1つで切る。** 保証台帳 `docs/guarantees.md` を持つリポでは、1本の Issue が触れる区切り（台帳のテストファイルごとの `###` の節）を1つにする。新しく起こすか、既存の1つに足す。作業の量ではなく約束の単位で切るためである。台帳の無いリポと `保証: なし` の Issue はこの基準の外にある

2 か 3 でまとめた Issue の保証節は、新たに宣言する保証を区切りごとに分けて書く。2 か 3 に当たるのにまとめないと決めたら、当たった基準と理由を報告に添える。

### 詳細セクション

- `内容` に収まらない仕様は `---` 以降に自由に展開する
- ファイルごとに見出しを立てる
- 実装順序が重要な場合は末尾に明記する

---
name: issue-draft
description: 相談者として Issue を設計し、GitHub Issue として draft ラベル付きで起票する。開放チャットで実装を頼まれたとき、または Issue を立てたいときに使う。コードは書かない（軽量経路の条件を満たす場合を除く）。
---

相談者として Issue を作成する。**実装しない**。起票したら止まる（実装は user が実行者を起動して行う）。

0. 軽量経路チェック: 以下3条件を**全て**満たすなら、Issue 化せずここで止まり、対象ファイルと理由を一言添えて相談者が直接編集してよい（単発例外の宣言は不要）
   1. diff がロジックに触れない（config・README・コメントなど）
   2. 保証台帳（`docs/guarantees.md`）に触れない（挙動の契約を変えない）
   3. 単一ファイル・数十行以内
1. テンプレート `.claude/skills/issue-draft/reference/issue-template.md` を読む
2. user の要望を要件・制約・対象ファイル（行の指し先まで）に整理する。曖昧な点はここで質問する
3. 一次情報を洗う（理由は `docs/ops/workflow.md`「一次情報を洗ってから書く」）
   - 作業の名前と主な語でリポ全体（文書・コード・`gh issue list --state all --search`）を検索し、当たった資料は全文を読む
   - 本文の `根拠` に、検索した語と読んだ資料を並べる
   - 振る舞いを説明する文書（README・`docs/`）が当たったら、直す分を `対象` に入れる
4. テンプレート後半の「Issue 作成ルール」（粒度・分割とまとめの基準）に従い設計する
   - 大きければ分割を、小さい Issue が並ぶならまとめを提案する
   - コードは書かず、要件・制約・指し先で書く。ただし自由度を残すと実行者が迷う・手戻りすると判断した箇所はコードを書いてよい
   - 保証節を必ず起草する。対象リポに保証台帳 `docs/guarantees.md` があれば、変更が触れる範囲の保証はそこから引いて「維持する保証」に列挙する（台帳が無ければ既存テストから直接読み取る）。台帳の記載に変更が出る場合（新保証・変更・廃止）は台帳を対象ファイルに含める
   - 動いている実行者とぶつからないかを確かめる。assignee の付いた open な Issue が作業中か PR 待ちである。その Issue の `対象` か PR の差分を見て、同じファイルの同じ箇所を書き換えるなら、先の Issue がマージされてから着手することを、その番号とともに本文と報告に添える。箇所は関数や節の単位で見る。別の関数や節を直すだけの Issue と、一覧の末尾へ追記するだけの Issue はぶつからない
   - 新たに宣言する保証が契約面（公開 API・CLI・外部から観測可能な振る舞い）なのに裏付けテストが対象に無い場合、台帳スコープ外を理由に素通りしない。報告でテスト欠落として明示し、本 Issue にテストを含めるか・理由を保証節に記録して見送るかを user に確認する
5. 機密マスク: 説明文中の固有の接続情報（ドメイン実値・公開ポート・本番絶対パス・VPN IP・SSH ユーザ名など）を `<PLACEHOLDER>` に置き換える。localhost・開発ポート・リポジトリ相対パスは伏せない
6. `gh issue create --label draft --title "{タイトル}" --body-file -` で起票する。本文は heredoc で標準入力から渡す
7. Issue の URL と概要を報告して止まる。user が保証節を裁可したら `draft` ラベルを外すよう伝える

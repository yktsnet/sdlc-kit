---
name: issue-draft
description: 相談者として Issue を設計し、GitHub Issue として draft ラベル付きで起票する。開放チャットで実装を頼まれたとき、または Issue を立てたいときに使う。コードは書かない（軽量経路の条件を満たす場合を除く）。
---

相談者として Issue を作成する。**実装しない**。起票したら止まる（実装は user が実行者を起動して行う）。

0. 軽量経路チェック: `docs/ops/roles.md`「例外」の軽量経路に当たるなら、Issue 化せずここで止まり、対象ファイルと理由を一言添えて相談者が直接編集してよい
1. テンプレート `.claude/skills/issue-draft/reference/issue-template.md` を読む
2. user の要望を要件・制約・対象ファイル（行の指し先まで）に整理する。曖昧な点はここで質問する
3. 一次情報を洗う（理由は `docs/ops/workflow.md`「一次情報を洗ってから書く」）
   - 作業の名前と主な語でリポ全体（文書・コード・`gh issue list --state all --search`）を検索し、当たった資料は全文を読む
   - 本文の `根拠` に、検索した語と読んだ資料を並べる
   - 振る舞いを説明する文書（README・`docs/`）が当たったら、直す分を `対象` に入れる
4. テンプレート後半の「Issue 作成ルール」の「粒度」に従い設計する
   - 分けるかまとめるかは、「粒度」の4つの基準を上から当てて決める。対象ファイルの数では決めない
   - 上限を超えるなら分割を、小さい Issue が並ぶならまとめを提案する
   - コードは書かず、要件・制約・指し先で書く。ただし自由度を残すと実行者が迷う・手戻りすると判断した箇所はコードを書いてよい
   - 保証節を必ず起草する。書き方はテンプレートの「保証節」に従う。保証台帳が無ければ、維持する保証は既存テストから直接読み取る
   - 動いている実行者とぶつからないかを確かめる。assignee の付いた open な Issue が作業中か PR 待ちである。その Issue の `対象` か PR の差分を、`docs/ops/workflow.md`「並行して動かす」の3つの組に当てる。当たるなら、先の Issue の番号を `待ち` に書き、報告に添える
   - 新たに宣言する保証が契約面（公開 API・CLI・外部から観測可能な振る舞い）なのに裏付けテストが対象に無い場合、台帳スコープ外を理由に素通りしない。報告でテスト欠落として明示し、本 Issue にテストを含めるか・理由を保証節に記録して見送るかを user に確認する
5. 機密マスク: `docs/ops/branch-and-pr.md`「コミットと PR に載せないもの」に挙げた固有の接続情報を `<PLACEHOLDER>` に置き換える。localhost・開発ポート・リポジトリ相対パスは伏せない
6. `gh issue create --label draft --title "{タイトル}" --body-file -` で起票する。本文は heredoc で標準入力から渡す
7. Issue の URL と概要を報告して止まる。user が保証節を承認したら `draft` ラベルを外すよう伝える
   - `## 待ちと手戻り` の節が `なし` でないのに `rework-read` のラベルが無いマージ済みの PR が10本を超えていたら、`rework-review` を回すよう報告に1行添える（`docs/ops/workflow.md`「束ねて Issue にする」）

     ```bash
     gh pr list --state merged --search "-label:rework-read" --limit 1000 --json body \
       --jq '[.[] | (.body // "" | gsub("\r";"")) | (capture("(?:^|\\n)## (?:待ちと)?手戻り\\n(?<s>.*?)(?:\\n## |\\z)"; "m") // null)
             | select(. != null) | .s | select(test("^\\s*なし\\s*$") | not)] | length'
     ```

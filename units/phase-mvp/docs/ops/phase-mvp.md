# MVP 期の駆動文書

方向性と構造が固まっていない立ち上がり期は、`PLAN.md`（何ができたら終わりか）と
`JUDGE.md`（なぜその実装なのか）が開発を進行させる。

## 入るもの

```text
PLAN.md / JUDGE.md                          リポ直下に置く。テンプレは skill が持つ
.claude/skills/mvp-docs/                    2文書の作り方・粒度・テンプレ
```

## 2文書は足場である

永続を求めない。README へ昇華した時点で削除する。

単一の仕様書を永続させようとすると、実装から乖離したまま残る。書かれた当時は正しく、
誰も更新せず、誰も間違いに気づかない。PLAN.md が腐らないのは、役目が終わったら消すからで
あって、丁寧に保守するからではない。

## 記録する判断の粒度

JUDGE.md に書くのは、選択肢が2つ以上あり・後から変えるとコストがかかり・コードを読んでも
理由が分からない判断だけ。**目安は1リポ 7±2 件。**

上限は重要な判断を落とすためではなく、細かい判断で本質的な判断を埋もれさせないためにある。
20 件並んだ JUDGE.md は、README にも設計判断の文書にも昇華できない。

粒度のフィルタとして一番効くのは「再検討の境界」（どの条件が変わったらこの判断を見直すか）
の1行である。これが書けない項目は、判断ではなく作業メモである。

## 畳み方

README を書く段で、2文書の中身を3つに仕分けて**削除する**。

| 中身 | 行き先 |
|---|---|
| 進捗・済んだ作業 | 捨てる（git log にある） |
| スコープ・やらないこと | README |
| 設計判断 | README の設計判断の節。全文が要るなら `docs/design-decisions.md` |
| 概念の名前と境界 | `context/domain.md` など、公開後も残る置き場 |

昇華した原本を残さない。README と原本の二重管理が始まると、片方だけ直される。

## 次のフェーズへ

保証台帳（`phase-guarantee`）が正式運用に上がる瞬間が、駆動文書の交代点である。
壊してはいけない振る舞いが台帳に固定された時点で、PLAN.md の役目は終わっている。

**台帳の格上げ・2文書の削除・CLAUDE.md のフェーズ記載の変更は、同じ1回の変更にまとめる。**
宣言だけ先に変えても実体は動かない。

## 取り込んだあとにやること

1. `CLAUDE.md` に現在のフェーズを書く（`フェーズ: MVP 期`）
2. `PLAN.md` を書く。`JUDGE.md` は最初の1件が出てから作る（空の枠を commit しない）

# 保証台帳

リリース後の駆動文書。**何を約束し、何を約束していないか**だけを記し、各約束は対応する
テストが継続検証する。

台帳は `docs/guarantees/` に置き、この配置は変えない。作業フローの skill と確認者がこのパスを読む。
入口の `README.md` に目的・分け方・書き方・引き方・運用を書き、約束は対象（モジュール・公開 API の群・
CLI のコマンドなど）ごとのファイルに「保証｜対応テスト」の表で並べる。形は `guarantee-audit` の手順3にある。

## なぜ README ではなく台帳か

リリース後は、仕様書を書くほどではない修正が積み重なり、最初の仕様書は実装から乖離していく。
README も同じように腐るが、腐っても何も起きない。

台帳が違うのは、各行にテストが紐づいている点にある。**破れば落ちるので、黙って腐らない。**

## 分業

保証の宣言（何が成り立つべきか）は user が承認し、テストの実装は実行者が書く。
この分業を **Guarantee-Driven Development (GDD)** と呼ぶ。

TDD がテストを先に書く規律だとすれば、GDD は約束の承認を先に行う規律である。
人間の仕事はテストを書くことから、約束を承認することへ移る。

テストそのものが正なのではない。承認された保証を実行可能な形に書き下ろしたものが正である。

## 何を載せるか

- **契約面のみ**（公開 API・CLI・配布物・外部から観測可能な振る舞い）。内部実装のテストは
  載せない
- **テストに裏付けられた保証のみ**。執行装置の無い約束を混ぜない
- 濃淡はリスクベースで決める。公開 API は厚く、内部実装は薄く、見た目は user の手動検証へ回す

README の `## Gaps` 節に、保証すべきだがテストが無いものを見送り理由ごと記録する。空になったら節ごと
削除する。

**ここに載っていない振る舞いは約束ではなく、予告なく変わりうる。** この一文を README の冒頭に
置く。台帳の価値は、載っているものより載っていないものの側にある。

## 追従

以後は Issue（または PR）の保証節と同一の変更で更新する。台帳の更新漏れは実装未完了として
扱う。台帳とテストの乖離は `guarantee-audit` の乖離チェックモードで定期的に検出する。

台帳のスコープ外に新しい契約面が生まれたときは、スコープに入れるかを起票時に判断する。
**対象外という記載を、素通りの根拠にしない。**

## 取り込んだあとにやること

1. `guarantee-audit` を実行して初版を敷く（テストが1本も無いなら、まず最初のテストから）
2. 承認が済んだら README のタイトルから `(Draft)` を外し、`CLAUDE.md` のフェーズを保証台帳期へ上げる（`フェーズ: 保証台帳期`）
3. README から台帳へリンクする。**到達できない台帳は無いのと同じ**

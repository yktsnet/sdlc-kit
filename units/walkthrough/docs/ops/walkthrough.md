# walkthrough

`walkthrough` skill が、中核の機能を1本作り終えたときに、その機能が何を受け取り、どう判断し、
何を出すかを書いた資料を作る。

**この文書と `.claude/skills/walkthrough/` は、`sdlc-kit` から取り込んだものである。** 取り込んだ
時点でこのリポの持ち物になった。以降はここを直す。

## 何のためにあるか

エージェントと進める実装は、人が理解するより速く進む。動くものが積み上がっても、なぜそう動くのかを
誰も説明できなければ、正しいと言える人がいない。次に手を入れる人は読み解くところから始め、読み解いた
内容もまたその人の頭の中にしか残らない。この認知負債は、作った直後がいちばん安く返せる。

この単位は、中核の機能を1本作り終えた時点で、その機能が何を受け取り、どう判断し、何を出すかを
1本の解説書に書き起こす。リポジトリ全体の地図ではなく、1つの機能を入口から出口まで追う。

読む人は3通りいる。

- **後から入った人。** その機能を最初に理解する入口になる
- **数か月後の自分。** そのときの自分は外の人と変わらない。担当が1人でも資料が要るのはこのためである
- **作っている最中の自分。** 1本作り終えた時点で、実際に何を作ったかを確かめてから次へ進む。
  確かめないまま積むと、作りながら方向を見失う

### 読む人がたどる段

資料は、次の段を順に深められるように書く。

1. **読む。** 輪郭、入力から出力までの経路、判断の規則をつかむ
2. **AI に問う。** 分からないところを、資料を前提にして質問する。資料の例は実際の出力と突き合わせて
   あるので、質問は正しい事実から始まる。資料が無いと、AI の説明がもっともらしいかどうかでしか
   判断できない
3. **手で確かめる。** 資料の例に判断の規則を当て、実際の出力と同じ値になるかを自分で追う
4. **動かす。** 手順の文書に沿って手元で立て、入力を変えて出力がどう変わるかを見る

**どの段まで進むか、いつ進むかは読む人が決める。** 理解が要るのは、その機能に手を入れるときや
説明を求められたときで、資料を作った時点とは限らない。作った時点で理解を強制しても、必要に
なったときには薄れている。資料は、必要になったときにいつでも深められる状態を先に用意しておく
ためにある。

**全部の機能には作らない。** 資料は実装と一緒に古くなるので、数を増やすと資料そのものが負債になる。
なぜこの機能を丁寧に説明するのかを1行で言えるものだけに作る。

## 取り込んだあとにやること

1. 資料の置き場を決め、`.claude/skills/walkthrough/reference/list-template.md` から一覧を置く。
   一覧は作成済みと予定の両方を持つ。どの中核の機能もいずれ作り終えるので、予定も先に並べておくと、
   次にどれを書くかが分かる
2. `.claude/skills/walkthrough/SKILL.md` の「このリポでの置き場」の穴を埋める。当てはまる置き場が
   無い行（仮置きを管理していない、画面が無い など）は消す
3. `CLAUDE.md` の skill 一覧に `/walkthrough` を足す

埋め残しはこれで探せる。`reference/` の型に残っている穴は、資料を書くときに埋めるものなので除く。

```bash
grep -rn "<[^>]*>" .claude/skills/walkthrough --exclude-dir=reference
```

## 使い方

中核の機能を1本作り終え、その実装が確定したあと（main に入ったあと）に `/walkthrough` を呼ぶ。
資料が指す実装がまだ動いていると、資料と実装が食い違う。

書く途中で、なぜそう作ったのかを実装からも記録からも読み取れない箇所が見つかることがある。skill は
それを資料の中で埋めず、書き終えたときに一覧で渡す。埋めるのは作った人の言葉であり、エージェントに
埋めさせない。

# grasp

## 目的

**アプリに初めて触る担当者が、どこから読めばよいかで迷わないようにする**。アプリ全体を1本の
概要資料にまとめ、呼ぶたびに古くなったところと足りないところを埋める。概要資料は、その担当者が
初見で分かるように書く。理由は `docs/ops/grasp.md`「何のためにあるか」にある。

**概要資料は正本への案内であり、正本の代わりではない**。骨組みと、詳しく読む文書を示すところまでにし、
厚くしすぎない。

概要資料はリポの開発の進み具合に合わせて育つ。始めたばかりのリポには薄い概要資料を、育ったリポには厚い
概要資料を書く。まだ作っていないものを先回りして書かず、作られた分だけ書き足す。

`walkthrough` を取り込んでいるなら、扱う範囲で分ける（`docs/ops/grasp.md`「walkthrough との分け方」）。

## 置き場

```
<概要資料の置き場>/
  overview.md   1行目に反映したコミット。呼ぶたびに作り込む
  src/          出力の見本（画面写真など）
```

前回からの差分は残さない。何が変わったかは `overview.md` の git の履歴で辿る。

## 章立て

H2 は、概要資料が答える問いで決める。

| 問い | H2 の名前の例 | H3 の例 |
|---|---|---|
| 何を受け取り、何を出すアプリか | 一言でいうと | — |
| 誰が、いつ、どこで何をするか | 使われ方 | 1回の流れ、段階ごとの作業、画面どうしのつながり、置き換える旧来の作業はどこへ行くか |
| データが入ってから外へ出るまでに、どの段階を通るか。どのコードが受け持つか | 処理の流れ | 段階とコードの対応、ある処理が走る条件 |
| 結果の正しさを決める規則は何か | アプリの中核の規則に合わせて名付ける（「金額の決まり方」「照合の決まり」など） | 規則の骨組み、規則が当たる範囲と当たらない範囲、まだ仮の規則 |
| 何を受け取り、何を渡すか。相手は誰か | 外とのつながり | 相手が増えて表に収まらなくなったら、相手ごとに分ける |
| アプリ全体に効く決まりは何か | 全体に効く決まり | 権限、記録、安全のための制約 |
| どこまでできているか | 到達点 | リリースやフェーズごとに、何があり何が無いか |

**初回に H2 の案を user に見せて決め、そのあとは名前も順番も変えない**。中核の規則は1つの H2 に
収まらなければ分けてよい（「金額の決まり方」と「確定と訂正」のように）。当てはまらない問い
（画面も利用者も無いアプリの「使われ方」など）は H2 を立てない。アプリが育ったら H3 を足して
受け止める。H2 で受け止められないものが出たら、足す前に user に確かめる。

**まだ作っていないものは1行で済ませる**。H2 の主題がリポにまだ無ければ、まだ無いことと、予定を
書いた文書への案内だけを書く。中身は、作られた回に書く。読み手にとっては、何がまだ
無いかも概要の一部である。

**正本の中身を写さない**。一覧・条件・権限・状態の表は、それぞれの正本に
ある。ここに書くのは、それらがどうつながっているかの説明と、読む文書への案内である。表を写すと、
正本が変わったときにここだけが古くなる。

読み手に前提とすること（プログラミング言語の書き方、開発の進め方など）は、`overview.md` の
冒頭の段落に書き、本文では説明しない。

## 0. 作業する場所を用意する

このリポで文書だけの変更を出す作業フローに従い、main を取り直してから作業するブランチを用意する。

## 1. 前回反映したコミットを読む

`overview.md` の1行目に、前回反映したコミットが書いてある。今回反映するのは `origin/main` の先頭である。
マージ済みのものだけを対象にし、作業中のブランチは含めない。

```bash
git fetch --prune
sed -n 's/^反映したコミット: `\([0-9a-f]*\)`.*/\1/p' <概要資料の置き場>/overview.md
```

**前回反映したコミットから `origin/main` が進んでいなければ、何もせずに終える**。定期に回したときに、
変化の無い回で1行目だけを替えるコミットを作らない。

```bash
git rev-list --count <前回>..origin/main   # 0 なら終える
```

`overview.md` が無ければ、決めた H2 だけの骨組みから作る。材料は正本の文書と
設計判断の文書、処理の段階ごとのコードのエントリポイントである。

## 2. 足りないところを決める

足りないところは4つから拾う。1回で全部を埋めず、今回扱うところを決めて user に示す。

**古くなったところ**。前回反映したコミットからの変化を読み、書いてあるのにもう違うところを探す。

```bash
git log --first-parent --format='%h %s' <前回>..origin/main
git diff --stat <前回>..origin/main
git diff <前回>..origin/main -- <正本の文書>
```

図や表は文書だけでなくコードからも起こしている。図や表の下の「正本：」の行に挙がったパスも
同じ範囲で差分にかける。パスは `<概要資料の置き場>/` からの相対で書いてある。

```bash
grep '^正本：' <概要資料の置き場>/overview.md
git diff --stat <前回>..origin/main -- <正本の行に挙がったパス>...
```

変更の意図は、マージした変更の説明で読む。

**新しく書けるようになったところ**。前回はまだ無かった主題が、この範囲で作られたところである。
1行で済ませていた H2 に中身を入れ、新しい段階・規則・相手には H3 を足す。

**user が言ったこと**。呼んだときに user が挙げた、読んだ担当者が迷った箇所や、聞かれて答えに詰まった
ことである。読み手の記録に残っているつまずきも拾う。

**まだ書けていないところ**。主題はあるのに H3 がまだ無い H2 と、図の基準に当たるのに文字だけの節である。

## 3. 書く

決めたところの H3 だけを書き直し、1行目を今回反映したコミットに替える。変わっていない H3 には
触れない。

```
反映したコミット: `<origin/main の短いハッシュ>` <YYYY-MM-DD HH:MM>
```

- 何を作ったかはコードと変更の説明から、なぜそう作ったかは正本の各文書と設計判断の文書から引く。
  理由がどこにも書かれていなければ埋めず、その箇所に「未確認」と書く
- 厚くしすぎない。迷ったら書かずに正本を指す。足りないところは、読み手が問いを立てて会話で補える
- 消えたものは消す。無くなった段や、やめた規則を「以前は」と書いて残さない

### 図

文字だけでは場面やつながりが見えにくいところを、図で補う。描くかどうか、幅、形と線種は
`.claude/skills/mermaid-diagram/SKILL.md` に従う。概要資料に固有の決まりは2つある。

- 「全体像」を**図の主題にしない**。描くと、分岐の無い一直線か、抽象度の混ざった図になる。
  図の前に何に答える図かを1文で書き、その節でいちばん大事な判断が1つのノードにまとめられて
  いたら、そのノードの中身を広げた図を描く
- **正本から起こす**。分岐の条件や終わり方を推測で書かない。図の下に「正本：」の行で何を正本に
  したかを書き、正本と図が食い違ったら正本を正として図を直す。次に呼んだときは、この行に挙げた
  パスを差分の対象にする

### 出力の見本

画面・帳票・ファイルのように、アプリが出すものの見た目は文字で説明するより見本を1つ置くほうが
早い。見本は実際に出して撮り、`src/` に置く。

- データはダミーデータか、テストが使う入力にする。実データを写さない
- 戻せない操作は、確認画面を撮ったら取り消して閉じる
- 見本のすぐ下に、撮ったコミットを「`<コミット>` で撮った」と書く。そのコミットから出力が変わった
  ものだけ撮り直し、この行を替える

## 4. 確かめる

- 状態（済・一部・未）や挙動を書いた文は、正本・コード・テストと照らしたか。照らせなかった文には
  「未確認」と書く
- H2 が初回に決めたまま、名前も順番も変わっていないか
- まだ作っていないものを、作ったように書いていないか
- リンクがすべて実在するファイルを指しているか
- ホスト名・IP・アカウント名のような固有の接続情報や、実データの値が入っていないか
- 図が正本と食い違っていないか

## 5. コミットして user に読んでもらう

```bash
git add -A <概要資料の置き場>/
git commit -m "全体像の資料を更新する"
```

コミットしたら、今回書いたところと、確かめられずに「未確認」と書いたところを user に示す。
初めて読む担当者の目で読んで迷ったところがあれば、同じブランチで直してコミットし直す。

push も PR も user の OK が出るまで行わない。

# 三役

決定と実装を分ける。決定と実行を同じ時間の中でやると、決定が実行の都合に引きずられ、
後から検証できなくなる。

| 役 | 担当 | 動く場所 |
|---|---|---|
| **user** | 決裁者。フェーズと保証の裁可、レビュー、マージ、デプロイ | — |
| **相談者** | 調査・設計・Issue 作成。**実装しない** | 開放チャット（main のチェックアウト） |
| **実行者** | Issue に基づく実装とローカルコミット。**リモートに触れない** | 専用の作業ブランチ |

「user」は役名である。このリポを使う人がそのまま当てはまる。

## 境界

- 相談者は Issue ファイルを書き出すところまで。書き終えたら止まる
- 相談者をエージェントが演じる場合も同じ。実装を頼まれたら Issue を `status: draft` で
  作成して止まり、user が保証節を裁可して `status: open` に変えてから実行者を起動する
- 実行者は Issue に基づき実装し、ローカルコミットで止まる。push・PR 作成・本番コマンドの
  実行は禁止。リモートへの公開は user のレビュー後
- 検証手順は実行者がコミットメッセージ本文の `## 検証手順` に書き、user が実施する

## 例外

Issue 駆動の硬直を緩めるため、次の3経路に限り相談者の直接編集を認める。

- **リアルタイム ops** — 事前に Issue 設計できない障害対応。そこから派生した実装は Issue 化する
- **単発例外** — user が「今回は例外で直接編集してほしい」と明示した回。対象ファイルと理由を
  一言添えて編集する
- **軽量経路** — diff がロジックに触れない・保証台帳に触れない・単一ファイル数十行以内の
  3条件をすべて満たす変更。宣言も不要

**常用化したらフェーズ自体を MVP 期へ戻す。** 例外が常態なら、分業がその段階に合っていない。

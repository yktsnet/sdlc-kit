# 作業フロー（クライアントあり）

作る範囲を、開発の外にいる依頼主の答えが決める場合に使う。受託の案件や、依頼部署の答えを
待って作る社内の案件が当たる。`flow-team` に重ねて入れる。開発側が1人でも、依頼主の答えを
待つ問いは Issue で追うので、土台は `flow-team` になる。

要件を決める人が開発側の中にいて、答えを待っても作業が止まらないなら、この単位は要らない。

## 入るもの

```text
.claude/skills/client-next/               届いた答えを回収し、次に着手する Issue を選ぶ。問いの型を同梱
docs/ops/client.md                        この文書
```

## 何が変わるか

`flow-team` では、作業を止めるのは実装である。依頼主がいると、作業を止めるのは答えになる。
答えは開発側の都合では早まらない。**答えを待って止まらず、仮に置いて作り、仮に置いたことを
残す。**

| | `flow-team` | クライアントあり |
|---|---|---|
| 範囲を決める人 | 開発側の user | 依頼主 |
| 曖昧さの埋め方 | 相談者が user に聞く | 依頼主への問いを立て、答えを待たずに仮に置く |
| 次に着手するもの | 裁可済みで assignee の無い Issue | そのうち、答え待ちの問いに掛かっていないもの |

## 問いの Issue

依頼主に聞くことは、`question` ラベルの Issue として立てる。作業の Issue の `仮定` に書くだけでは、
依頼主へ渡したか、答えが来たかを追えない。

- 1つの問いに1つの Issue。答えが1つに定まる形で聞く
- 本文に、仮に置いた案と、その案で作る Issue の番号を書く
- 依頼主から答えが来たら、受け取った人がその答えをコメントに写して閉じる。依頼主との
  やりとりの経路（メール・チャット・打ち合わせ）は問わない。**正本はこの Issue に置く**

## 仮に置いて作る

作業の Issue は、答えを待たずに起票して裁可を受けてよい。仮に置いた判断は `仮定` に書き、
問いの Issue の番号を添える。保証節も仮の案で書く。

答えが来て仮の案と合っていれば、何もしなくてよい。違っていれば、作った Issue を開き直さず、
答えに合わせる新しい Issue を立てる（`flow-team`「派生 Issue」と同じ）。

**仮に置いたものは、答えが来て決着するまで追う。** 閉じた作業の Issue でも、仮の案に掛かっている問いが
開いているうちは、依頼主に見せられる完成ではない。

## 依頼主に見せる現在地

依頼主が知りたいのは、何ができていて、何が自分の答え待ちかである。2つの一覧で答えられる。

- できたもの: 閉じた作業の Issue のうち、開いた問いに掛かっていないもの
- 答え待ち: 開いている `question` の Issue と、それぞれに掛かっている作業の Issue

## 取り込んだあとにやること

1. `flow-team` を先に取り込んでおく
2. GitHub に `question` ラベルを作る（`gh label create question`）
3. `CLAUDE.md` に、この文書への参照を1行書く。**規約そのものを書き写さない**

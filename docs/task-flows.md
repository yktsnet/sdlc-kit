# 作業フローの2手法

**着手前の合意をどこに置くか**で手法が2つに分かれる。Issue ファイルに置く「Issue 版」と、
PR 本文に置く「単発版」である。**どちらもリポジトリごとに1つだけ選ぶ。**

2手法は、同じものを違う場所に置いているだけである。どちらも、何をやるか・何が真になれば
終わりか・どう確かめたかを残す。違うのは置き場と段の数で、残るものは変わらない。

配布物は `units/flow-issue/` と `units/flow-single/`。

## 違い

| | Issue 版 | 単発版 |
|---|---|---|
| 合意の置き場 | `issues/{id}_{slug}.md` の保証節 | PR 本文の `## 完了条件` |
| 残作業の一覧 | `issues/` の `status: open` | open な PR の一覧 |
| 段の数 | 3（起票 → 実装 → 完了） | 2（実装 → 引き渡し） |
| skill | `new-issue` / `pr-workflow` | `work` / `hand-off` |
| ブランチ | `claude/{id}-{slug}` | `work/{slug}` |
| 分業 | 三役（user / 相談者 / 実行者） | 実装者と user |

ほかは同じである。ブランチの単位＝PR の単位、着手前の保証を user が裁可する、マージは人が
押す、証拠の無い完了を書かない。この4点は両方に入っている。

## どちらを選ぶか

Issue ファイルは「置き場をもう1つ持つ」ことなので、**それに見合う仕事がある場合にだけ
得になる。**

Issue 版を選ぶ条件。ひとつでも当たれば台帳が要る。

- 作業が1本の PR に収まらない。複数の PR にまたがる、あるいは着手が数日後になる
- 着手前の合意を PR より前に残す必要がある。仕様の確認や承認が PR を出すより先に立つ
- 担当者が複数いて、誰が何を持っているかが PR の一覧から読めない
- 起票と着手が別の人・別の日になる

単発版を選ぶ条件。

- 変更が1本の PR に収まる。着手から提出まで同じセッションで終わる
- 担当が実質1人
- 残作業の一覧が open な PR で足りる

迷ったら単発版から始める。台帳は後から足せるが、使われない台帳は更新が止まり、実態と
食い違ったまま残る。**片方にだけ更新が入る状態が、台帳を持つ最大の損失である。**

## 乗り換える合図

単発版 → Issue 版。

- open な PR が「着手待ち」を表すようになってきた（PR が実装より先に立つ）
- 「あれはどうなったか」が PR の一覧から答えられない
- 着手前の合意を対話でしか残しておらず、後から確認する手段が無い

Issue 版 → 単発版。

- Issue の粒度が PR 1本と1対1になり、起票が事務作業になっている
- close を書くためだけのコミットが増えている

# 作業フローの3つの枠

作業フローは**誰と作るか**で3つに分かれる。1人で作る `solo`、チームで作る `team`、依頼主の
答えが範囲を決める `client` である。**リポジトリごとに1つだけ選ぶ。**

3つは、同じものを違う場所に置いているだけである。どれも、何をやるか・何が真になれば
終わりか・どう確かめたかを残す。違うのは置き場と、合意に加わる人である。

配布物は `units/flow-solo/`・`units/flow-team/`・`units/flow-client/`。
回し方の例は [flows/solo.md](flows/solo.md)・[flows/team.md](flows/team.md)・[flows/client.md](flows/client.md) にある。

## 違い

| | solo | team | client |
|---|---|---|---|
| 作る人 | 1人。決める人と作る人が同じ | 複数 | 開発側の人数は問わない。範囲は依頼主が決める |
| 合意の置き場 | PR 本文の `## 完了条件` | GitHub Issue の保証節 | team と同じ。依頼主への問いも Issue にする |
| 残作業の一覧 | open な PR の一覧 | open な Issue の一覧 | team の一覧と、答え待ちの問いの一覧 |
| 段 | 実装 → 引き渡し | 起票 → 実装 | team の2段に、答えの回収と次の選択を足す |
| skill | `work` / `hand-off` | `issue-draft` / `issue-work` | team の2つと `client-next` |
| ブランチ | `work/{slug}` | `issue/{N}-{slug}` | team と同じ |
| 分業 | 実装者と user | 三役（user / 相談者 / 実行者） | team と同じ |

ほかは同じである。ブランチの単位＝PR の単位、着手前の保証を user が裁可する、マージは人が
押す、証拠の無い完了を書かない。この4点は3つすべてに入っている。

フェーズ（`phase-mvp` / `phase-guarantee`）は別の軸で、どの枠とも組める。チームでも立ち上がり期は
あり、1人でも保証台帳は効く（[lifecycle.md](lifecycle.md)）。

## どれを選ぶか

**solo** は、決める人と作る人が同じ場合に選ぶ。何を作るかを決めた人がそのままエージェントと
完了条件を決め、作って PR を出す。合意は PR 本文に置けば足り、台帳は要らない。

作る人が複数いるなら **team** である。誰が何を持っているか、何が裁可済みかを、作る人どうしで
共有する必要があり、その共有の置き場が Issue になる。

作る範囲を、開発の外にいる依頼主の答えが決めるなら **client** である。作業を止めるのが実装ではなく
答えになるので、答えを待たずに仮に置いて作り、何を仮に置いたか・何が答え待ちかを残す。
答えを待つ問いは Issue で追うので、開発側が1人でも土台は team になる。

Issue は「置き場をもう1つ持つ」ことなので、**共有する相手がいる場合にだけ得になる。**
使われない台帳は更新が止まり、実態と食い違ったまま残る。台帳と実態の片方にだけ更新が入る状態が、
台帳を持つ最大の損失である。

## 乗り換える合図

solo → team。

- 作る人が2人目以上になり、誰が何を持っているかを PR の一覧だけでは共有できない
- open な PR が「着手待ち」を表すようになってきた（PR が実装より先に立つ）
- 着手前の合意を対話でしか残しておらず、後から確認する手段が無い

team → client。

- 依頼主の答えを待つ問いが積み上がり、次に作るものを答えの有無で選ぶようになった

team → solo。

- 作る人が1人に戻り、起票が事務作業になっている

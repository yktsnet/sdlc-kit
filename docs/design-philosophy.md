# 何を型にするか

配布物を足すかどうかの判断基準。ここに当たらないものは配らない。

**配るのは1人で固めた型だが、使うのはチームである。** ここで挙げる理由はどれも、読み手や
書き手が複数いることを前提にしている。1人で回している間は、型が無くても頭の中で足りてしまう。

## 通底する前提

**注意し続ける人間を前提にしない。**

規約は読み手の集中力に依存し、集中力は疲れると落ちる。守られるかどうかが人の状態に
左右される仕組みは、そもそも作らない。禁止は文書ではなく機構に置き、検証はローカルと CI の
二か所で同じものを回す。文書に書いて守らせるのは最後の手段であって、最初の手段ではない。

この前提が最も露骨に出るのがテストの定義で、ここでは「実行者が壊したことに自分で気づく
ための装置」と規定する。人が注意して見つけるのではなく、壊した本人が提出前に気づく経路を
用意する。

## 型にするのは、エージェントが自力で越えられないところだけである

コードを書く、変更点を要約する、といった作業はその場で頼めば足りる。型が要るのは3つで、
配布物はすべてこのいずれかに当たる。

- **人が判断すべき点を落とさせない** — 保証の裁可、完了条件の宣言
- **セッションを越えて残す** — 駆動文書、Issue ファイル、台帳
- **担当者が替わっても揃う** — 文体、ブランチと PR の扱い、置き場の規則、日報

効くのは2つ目と3つ目で、この2つは同じことの裏表である。残っていても書式が人ごとに違えば
読むのに手間がかかり、揃っていても中身が残らなければ読むものが無い。以降はこの2つを扱う。

## 残るとは、辿れることである

残すべきは成果物ではない。**作業者が何を考えてそこへ至ったかが、後から辿れる形で残ること**
である。残す先はリポジトリで、作業者が何人いても変わらない。軌跡は人ごとに分かれず、1枚に
集まる。

動くものができれば仕事は進む。だが動くものだけを残すと、なぜそうしたかは作業者の頭の中に
しか無い。1週間後に本人が読み返しても、コミットとファイルを1つずつ辿って思い出す作業になる。

**「後から聞けばよい」は成り立たない。** 聞かれる側は、聞かれた時点の理解で答える。判断した
時点で何を知っていて、何を知らなかったかは、そのとき書いておかないと再現できない。

## 置き場が、別々の問いに答える

置き場は5つある。**答える問いと粒度が違うので、互いの代わりにならない。**

| 置き場 | 答える問い | 粒度 |
|---|---|---|
| `PLAN.md` | 全体としてどこへ向かっているか。何がどれだけ残っているか | 計画全体 |
| Issue の保証節／`work` の完了条件 | いま何をやるか。何が真になれば終わりか | 変更1本 |
| PR 本文 | 何をどう変えたか。なぜ終わったと言えるか | 変更1本 |
| `JUDGE.md` | なぜその案を採り、何を捨てたか | 判断1件 |
| 保証台帳 | いま何を約束していて、何を約束していないか | リポの公開面 |

PR を全部読んでも全体の向かう先は出てこないし、`PLAN.md` を読んでも個々の変更が正しいかは
分からない。**1つ欠けると、残りを全部読んで推測する作業が戻ってくる。**

とくに `JUDGE.md` が埋める穴は大きい。設計判断は本来、変更のあちこちに散らばって現れる。
1ファイルずつ辿れば痕跡はあるが、見えるようで見えない。1枚に集めて初めて、作業者の思考
として読める。

**日報はこの5つに入らない。** 日報が答えるのは「その人が1日に何を動かしたか」で、問いの主語
が人であり、読み手も外（上司・ステークホルダー）にいる。5つは主語がリポジトリと変更で、
読み手は後からこの仕事を辿る人である。だから日報だけが担当者ごとに分かれ、5つは分かれない
（`daily-report`）。

**決め手をエージェントに埋めさせない。** もっともらしい理由を補うと、読んだ人がそれを判断の
根拠として扱う。判断した人の言葉が無いなら、空のまま残す。

## 完走していなくても読める

置き場が揃っていることの効き目は、**途中の状態で読めること**にある。どこまで進んでいるか
（`PLAN.md` の残り）、何を考えて進めてきたか（`JUDGE.md`）、個々の変更をどう確かめたか
（PR 本文の証拠）。完成を待たずに、これだけ分かる。

逆に言えば、途中で止まっているものほど、この形で残っている価値が大きい。

## 読めることが、話せることになる

同じものを本人以外も読める。

- **本人が振り返れる。** 判断した時点の理由が残っているので、変えるべきか続けるべきかを
  自分で判定できる
- **他の人が参考にできる。** 同じ場面に来た人が、下敷きとして読める
- **互いに意見を言える。** レビューが人の記憶ではなく記録に対して行われる。「なぜこうしたか」
  を尋ねるところから始めずに済み、書いてある理由に対して直接話せる

3つとも、**同じものが1枚に集まっているから**成り立つ。担当者ごとに `PLAN.md` があれば全体の
向かう先はどこにも無く、`JUDGE.md` が分かれていれば、隣の人がなぜその設計なのかを読めない。
人が増えるほど、集まっていることの効き目が大きくなる。

## 揃うと、比べられる

同じ形の文書が担当者の数だけ並ぶと、作業の経過がそのまま見える状態になる。完了条件の切り方、
捨てた選択肢の書き方、証拠の取り方は、同じ型で書いても人によって差が出る。型が揃っているから、
その差を書式の差ではなく中身の差として読める。人ごとに置き場も書式も違えば、読み取れるのは
書式の差だけで、仕事の差には届かない。

だから標準化された成果物が出ることは、そのまま現在地が測れることを意味する。測れれば、次に
上げる軸が決まる。**育成のために別の仕組みを足す必要は無い。この型を回して開発すること自体
が、その役を果たす。** 型を配る理由のうち、チームに入れるときに最も大きいのはこれである。

## 導入の順序

1. **作る前に型を決める** — 何を作るのかが決まらないと、何を遮断するかも、何を検証手段に
   するかも決まらない
2. **禁止を文書でなく仕組みに置く**（`guards`）— 遮断が無い状態で知識を増やすと、事故の
   速度だけが上がる
3. **読まれる場面ごとに知識を置く**（`doc-style` と各 `docs/ops/`）— 置き場が定まらないと
   保証を書く土台が無い
4. **守る保証を先に裁可する**（`phase-guarantee`）
5. **決める人と作る人を分ける**（`flow-issue`）

順序には依存がある。保証が固まる前に分業すると、実行者が何を壊してはいけないか分からない
まま走る。

**チームに入れるときの最小構成は 1〜3。** エージェントが走るなら、公開物の有無にかかわらず
必ず要る。4〜5 は、公開物を持つとき、または複数人・複数セッションで並行し始めたときに足す。

## 参照ではなくコピーで配る

配布元を参照させると、そのリポを触る人が配布元を持っていない場合に手順が再現できない。

各単位は `docs/ops/` の文書と、そのリポの事情を書き込む穴（`<検証コマンド>` など）を
持っていて、**リポジトリの中にあって初めて成立する**。取り込んだ時点でそのリポの持ち物に
なり、以降はコピー先を直す。書き換えた結果が配布元と食い違ってよい。

配布元の不備に気づいたらこのリポを直す。コピー先を直しても配布元には戻らない。逆に、
コピー先で入れたリポ固有の書き換えを配布元へ持ち込まない。穴のままにしておく。

`install.sh --diff` は、取り込み以降に配布元が何を変えたかを見せる。当てるかどうかは
人が決める。**自動では更新しない。**

## 各リポで埋める穴

| 穴 | 例 |
|---|---|
| 検証コマンド | `pnpm check` / `npm run build` / `cargo test` |
| 遮断したいコマンド | デプロイ、本番への接続、生成物への直接編集 |
| 文書の言語 | 見出しと本文の言語、コミットメッセージの言語 |

## だから守ること

配布物のあちこちに書いてある規範は、すべてここから出ている。

| 規範 | 理由 |
|---|---|
| 保証と完了条件は着手前に裁可する | 後から決めると、できたものに合わせた条件になる |
| 証拠の無い完了を書かない | 実装した記憶は証拠にならない。何を実行すれば真かを先に決める |
| 判断の決め手をエージェントに埋めさせない | 埋めた理由はもっともらしいが、作業者が考えたことではない |
| 計画と判断は1枚に集める | 人ごとに分けると、全体の向かう先と設計の理由がどこにも無くなる |
| `PLAN.md` は残りだけを持つ | 終わったものを残すと、どこが最新か分からなくなる |
| 駆動文書は昇華したら削除する | README と原本の二重管理が始まると、片方だけ直される |
| 台帳にはテストに裏付けられた保証だけを載せる | 執行装置の無い約束は、破れても誰も気づかない |
| PR は裁可のあとに出す | 出してから直すと、レビューの履歴が実装途中の状態に対するものになる |
| マージは人が押す | 自分の変更を自分で公開に載せない |
| 禁止は文書でなく deny とフックに置く | 文書に書いた禁止は、読み手の集中力が落ちた時点で効かなくなる |

**これらを守らないなら、置き場だけ作っても軌跡は残らない。** 形式だけの `PLAN.md` と、
エージェントが書いた理由の並ぶ `JUDGE.md` は、読む人を誤らせるぶん、無いより悪い。

## 単位を足すとき

`units/<name>/` は取り込み先の配置をそのまま写す。深さを揃えてあるので、コピーは
`cp -R units/<name>/. <取り込み先>/` の一手で済む。

足したら `install.sh` の単位リストと `units/README.md` を直す。

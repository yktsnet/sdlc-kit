# 何を型にするか

配布物を足すかどうかの判断基準。ここに当たらないものは配らない。

## 通底する前提

**注意し続ける人間を前提にしない。**

規約は読み手の集中力に依存し、集中力は疲れると落ちる。守られるかどうかが人の状態に
左右される仕組みは、そもそも作らない。禁止は文書ではなく機構に置き、検証はローカルと CI の
二か所で同じものを回す。文書に書いて守らせるのは最後の手段であって、最初の手段ではない。

この前提が最も露骨に出るのがテストの定義で、ここでは「実行者が壊したことに自分で気づく
ための装置」と規定する。人が注意して見つけるのではなく、壊した本人が提出前に気づく経路を
用意する。

## 型にするのは、エージェントが自力で越えられないところだけである

コードを書く、変更点を要約する、といった作業はその場で頼めば足りる。型が要るのは3つで、
配布物はすべてこのいずれかに当たる。

- **人が判断すべき点を落とさせない** — 保証の裁可、完了条件の宣言
- **セッションを越えて残す** — 駆動文書、Issue ファイル、台帳
- **担当者が替わっても揃う** — 文体、ブランチと PR の扱い、置き場の規則

最も大きいのは2つ目である。動くものだけを残すと、なぜそうしたかは作業者の頭の中にしか
残らない。

## 導入の順序

1. **作る前に型を決める** — 何を作るのかが決まらないと、何を遮断するかも、何を検証手段に
   するかも決まらない
2. **禁止を文書でなく仕組みに置く**（`guards`）— 遮断が無い状態で知識を増やすと、事故の
   速度だけが上がる
3. **読まれる場面ごとに知識を置く**（`doc-style` と各 `docs/ops/`）— 置き場が定まらないと
   保証を書く土台が無い
4. **守る保証を先に裁可する**（`phase-guarantee`）
5. **決める人と作る人を分ける**（`flow-issue`）

順序には依存がある。保証が固まる前に分業すると、実行者が何を壊してはいけないか分からない
まま走る。

**最小構成は 1〜3。** 公開の有無やチーム規模によらず効く。エージェントが走るなら
必ず要る。4〜5 は、公開物を持つとき、または複数人・複数セッションで並行し始めたときに足す。

## 参照ではなくコピーで配る

配布元を参照させると、そのリポを触る人が配布元を持っていない場合に手順が再現できない。

各単位は `docs/ops/` の文書と、そのリポの事情を書き込む穴（`<検証コマンド>` など）を
持っていて、**リポジトリの中にあって初めて成立する**。取り込んだ時点でそのリポの持ち物に
なり、以降はコピー先を直す。書き換えた結果が配布元と食い違ってよい。

配布元の不備に気づいたらこのリポを直す。コピー先を直しても配布元には戻らない。逆に、
コピー先で入れたリポ固有の書き換えを配布元へ持ち込まない。穴のままにしておく。

`install.sh --diff` は、取り込み以降に配布元が何を変えたかを見せる。当てるかどうかは
人が決める。**自動では更新しない。**

## 各リポで埋める穴

| 穴 | 例 |
|---|---|
| 検証コマンド | `pnpm check` / `npm run build` / `cargo test` |
| 遮断したいコマンド | デプロイ、本番への接続、生成物への直接編集 |
| 文書の言語 | 見出しと本文の言語、コミットメッセージの言語 |

## 単位を足すとき

`units/<name>/` は取り込み先の配置をそのまま写す。深さを揃えてあるので、コピーは
`cp -R units/<name>/. <取り込み先>/` の一手で済む。

足したら `install.sh` の単位リストと `units/README.md` を直す。

# 2つの駆動文書

開発文書には寿命がある。単一の仕様書を永続させようとせず、フェーズごとに駆動文書を
交代させる。

**駆動文書**とは、その時期の開発を進行させ、更新され続ける文書のこと。リポが今どちらの
フェーズにあるかは user が決め、`CLAUDE.md` に書く。

## MVP 期 — PLAN.md / JUDGE.md

方向性と構造が固まっていない立ち上がり期。何を作れば完成かを `PLAN.md` が、なぜその実装かを
`JUDGE.md` が保持し、エージェントはこれを更新しながら実装する。

この2つは足場であって、永続を求めない。公開時に README へ昇華し、**昇華したら削除する**。
判断の全文が要るなら `docs/` へ移し、README と原本の二重管理を残さない。経緯は git にある。

配布物は `units/phase-mvp/`。

## Issue ドリブン期 — 保証台帳

リリース後は、仕様書を書くほどではない修正が積み重なり、最初の仕様書は実装から乖離していく。
そこで駆動文書を保証台帳（`docs/guarantees.md`）へ交代させる。

台帳は「何を約束し、何を約束していないか」だけを記し、各約束は対応するテストが継続検証する。
README と違い、**破れば落ちるため黙って腐らない**。

配布物は `units/phase-guarantee/`。

## 交代点

台帳が正式運用に上がる瞬間が交代点である。壊してはいけない振る舞いが台帳に固定された時点で、
`PLAN.md` の役目は終わっている。

フェーズ移行とはこの交代のことであり、宣言だけを先に変えても実体は動かない。
**台帳の格上げ・駆動文書の廃棄・`CLAUDE.md` の記載変更は、同じ1回の変更にまとめる。**

## どこから入るか

既存リポに後から敷くなら、`phase-guarantee` だけを入れて構わない。立ち上げ済みのリポに
`PLAN.md` を書いても、書いた時点で足場としての役目が無い。

新規リポは `phase-mvp` から始め、リリースの段で `phase-guarantee` を足す。
